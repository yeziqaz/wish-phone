# 「AI 角色聊天」生态数据格式与标准调研
> 面向「愿望机」：纯前端 PWA + 自带 OpenAI 兼容 API + IndexedDB 存档。目标 = 让用户把现成角色卡 / 世界书粘进来就能用。
> 调研时间：2026-10-30。所有字段名均来自一手规范文件或官方源码，凡未读到原文的一律标注 **未核实**。

---

## 1. 一句话总结

这个领域的事实标准是三件套：**Character Card V2（`TavernCardV2`，`spec: "chara_card_v2"`）作为角色卡载体 + SillyTavern 的 World Info / `character_book` 作为世界书 + PNG `tEXt` 的 `chara` chunk 作为分发容器**；V3（`chara_card_v3` / `ccv3` chunk / `.charx`）已定稿并被 SillyTavern 双向读写，但社区存量卡片绝大多数仍是 V2/V1。

**愿望机要兼容到哪一层**：第一版吃透 V1 + V2（JSON 与 PNG 两种投喂方式）、吃透 `character_book` 与 ST 独立世界书的导入、按 ST 的 prompt 组装惯例发消息；V3 只做「原样收下、原样存回、不丢字段」的兼容层（`spec` 探测 + 未知字段进 `extensions` 保留 + 识别 `ccv3` chunk），不实现 assets / CHARX / decorators。

### 2.3 有没有 V3？

有。[kwaroran/character-card-spec-v3 / SPEC_V3.md](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)（MIT 许可，[LICENSE](https://github.com/kwaroran/character-card-spec-v3/blob/main/LICENSE)）。
V3 的 `CharacterCardV3` 是 V2 的**超集**（`spec: 'chara_card_v3'`，`spec_version: '3.0'`），差异如下：

| 变化类型 | 内容 |
|---|---|
| 新增 | `nickname?: string` —— `{{char}}` / `<char>` / `<bot>` **SHOULD** 优先替换成它，没有才用 `name` |
| 新增 | `assets?: Array<{type, uri, name, ext}>` —— 立绘/背景/表情/用户头像；`uri` 支持 `embeded://`、`ccdefault:`、http(s)、base64 data URL；缺省时**MUST**等价于 `[{type:'icon', uri:'ccdefault:', name:'main', ext:'png'}]` |
| 新增 | `creator_notes_multilingual?: Record<string,string>`（ISO 639-1 语言码键，无地区码） |
| 新增 | `source?: string[]`（卡来源 ID/URL；**SHOULD** 只追加不修改） |
| 新增 | `group_only_greetings: string[]`（**MUST** 存在，可为空；群聊专用问候） |
| 新增 | `creation_date?` / `modification_date?`（Unix 秒，UTC） |
| 变更 | `creator_notes` 语义变为"`creator_notes_multilingual` 缺失时的兜底 / `en` 兜底" |
| 变更 | `character_book` 的类型名改为 `Lorebook`，条目新增 **`use_regex: boolean`**；`constant` 从"可选实现"升级为"required to implement" |
| 变更 | 引入 `@@decorator`（写在 `content` 里，`@@` 开头到行尾，如 `@@depth 5`、`@@position`、`@@role`、`@@activate_only_every`）与 `@@@` 回退链 |
| 变更 | 明确 CBS（`{{char}}`/`{{user}}`/`{{random:}}`/`{{pick:}}`/`{{roll:}}`/`{{// }}`/`{{hidden_key:}}`/`{{comment:}}`/`{{reverse:}}`） |
| 容器 | PNG 用 `ccv3` chunk（V2 是 `chara`），两者并存时**SHOULD**优先 `ccv3`；新增 `.charx`（zip，根目录 `card.json` + assets） |
| 单独导出世界书 | `{ spec: 'lorebook_v3', data: Lorebook }` |

未核实：是否存在 V3 之后的正式规范版本。V3 仓库最后推送时间为 2024-07-20（GitHub API 元数据），可视为当前最新。

## 3. 世界书 / Lorebook 字段表

### 3.1 两种物理形态（导入时必须都吃）

1. **卡内世界书**（V2/V3 规范）：`data.character_book = { name?, description?, scan_depth?, token_budget?, recursive_scanning?, extensions, entries: [...] }`，`entries` 是**数组**。
2. **SillyTavern 独立世界书 JSON**（`.json` 文件，实际生态里更常见）：顶层 `{ "entries": { "0": {...}, "1": {...} } }`，`entries` 是**以 uid 为键的对象**。实证样本：[default/content/Eldoria.json](https://github.com/SillyTavern/SillyTavern/blob/HEAD/default/content/Eldoria.json)。ST 的解析/转换代码：[world-info.js `convertCharacterBook()`](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/world-info.js) 与 `originalWIDataKeyMap`。

### 3.2 书级字段

| 规范字段名 | ST 独立世界书字段 | 类型 | 含义 | 一版支持 |
|---|---|---|---|---|
| `name` | （文件名） | `string?` | 标识，不进 prompt | ✅ |
| `description` | — | `string?` | 备注，不进 prompt | ✅ 存 |
| `scan_depth` | 全局设置（可被条目 `extensions.scan_depth` 覆盖） | `number?` | 只在最近 N 条消息里找关键词；0 = 不扫（只评估递归与 Author's Note） | ⚠️ 一版可固定 4（ST 的 `DEFAULT_DEPTH = 4`） |
| `token_budget` | 全局 Budget/% | `number?` | 超预算时丢低优先级条目；constant 先入，然后 order 大的先入 | ❌ 一版不做，占位 |
| `recursive_scanning` | 递归扫描 | `boolean?` | 条目 `content` 命中可再触发别的条目 | ❌ 一版不做，占位 |
| `extensions` | — | `Record<string,any>` | **MUST** 存在，未知键不得销毁 | ✅ 透传 |

### 3.3 条目字段

| 规范字段名 | ST 名 | 类型 | 含义与匹配规则 | 一版支持 |
|---|---|---|---|---|

| `secondary_keys` | `keysecondary` | `string[]?` | 次级关键词，配合 `selective` | ✅（可选） |

| （`selectiveLogic`，非规范字段） | `selectiveLogic` | `number` | 逻辑：`AND_ANY=0`、`NOT_ALL=1`、`NOT_ANY=2`、`AND_ALL=3`（源码 [world-info.js:33-38](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/world-info.js)） | ⚠️ 一版实现 0/3 即可 |
| `content` | `content` | `string` | 命中后插入 prompt 的正文；**同一条只插一次**；空串则什么都不插。V3 里可能带 `@@decorator` | ✅ |

| `insertion_order` | `order` | `number` | 越小越靠前插入；文档口径：order 越大越靠后（越靠近生成点，影响越大）；100 在 250 之前出现 | ✅ |
| `case_sensitive` | `caseSensitive`（也在 `extensions.case_sensitive`） | `boolean?` | 未定义时实现可自选 | ✅ |

| `position` | `position` | `'before_char'\|'after_char'` / ST 是数字 | 卡内规范只有前后两个值；ST 数字枚举：`before=0, after=1, ANTop=2, ANBottom=3, atDepth=4, EMTop=5, EMBottom=6, outlet=7`（[world-info.js:855-864](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/world-info.js)） | ✅ 只支持 before/after + depth 近似 |
| `id` | `uid` | `number\|string?` | 仅标识，不进 prompt | ✅ 存 |
| `comment` | `comment` | `string?` | 备注标题，不进 prompt；空时可回填第一个 key | ✅ 展示 |
| `name` | — | `string?` | AgnAI 兼容的标识名 | ✅ 存 |
| `priority` | — | `number?` | AgnAI 兼容；预算不够时低值先丢 | ❌ 占位 |
| `use_regex` | —（靠 key 写法判定） | `boolean` | V3 新增：keys 按正则解释；非法正则**MUST**视为不命中 | ❌ 占位 |
| `extensions` | — | `Record<string,any>` | ST 的真实个体参数全塞这里：`depth`、`position`、`probability`、`role`、`match_whole_words`、`exclude_recursion`、`prevent_recursion`、`delay_until_recursion`、`display_index`、`group`、`group_weight`、`group_override`、`vectorized`、`sticky`、`cooldown`、`delay`、`triggers`、`scan_depth`、`use_group_scoring`、`ignore_budget`、`match_persona_description` …（映射表见 [world-info.js `originalWIDataKeyMap`](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/world-info.js) 与 `convertCharacterBook`） | ✅ **原样透传**，实现 `depth`/`position`/`probability`/`match_whole_words` 中的 depth |

补充（来自 ST 官方文档 [World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)）：
- `position` 里的 **@ D（atDepth）**：Depth 0 = prompt 最底部，角色是 system/user/assistant 三种角色之一（ST 的角色枚举 `SYSTEM=0, USER=1, ASSISTANT=2`，`extension_prompt_roles`）。
- **扫描文本默认带说话人前缀**（Include Names 默认开），即扫的是 `Alice: 你好` 而不是 `你好`——这决定了"用名字当关键词"的条目能不能触发。
- **Probability**：命中后仍有 `probability%` 的概率插入。
- **Inclusion Group**：同组条目只留一个（按 group weight 随机，或按 order 取最高）。
- **Timed Effects**：`sticky`（命中后保持 N 条）、`cooldown`（N 条内不能再触发）、`delay`（至少 N 条消息后才可触发）。
- 预算耗尽后不再插入任何条目；**constant 条目最先插，其次 order 大的**。

## 4. PNG 角色卡藏 JSON 的确切做法

### 4.1 事实澄清
- V1 规范原文写的是「PNG/APNG: JSON string encoded in base64 inside the **"Chara" EXIF** metadata field」——这个措辞**不准确**：PNG 没有 EXIF，实际实现是 **PNG `tEXt` chunk，keyword = `chara`**（小写）。V3 规范写对了：`tEXt` chunk 名 `ccv3`。
- 参考实现：[SillyTavern `src/character-card-parser.js`](https://github.com/SillyTavern/SillyTavern/blob/HEAD/src/character-card-parser.js)（Node 端，写/读）与 [`public/scripts/utils.js` `extractDataFromPng()`](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/utils.js)（浏览器端，手写 PNG 解析）。

### 4.2 编码步骤（可直接照做）

**写（导出 PNG 卡）**
1. `json = JSON.stringify(card)`（V2：顶层 `spec`/`spec_version`/`data`）。
2. UTF-8 字节化：`const bytes = new TextEncoder().encode(json)`。**不能直接 `btoa(json)`**——`btoa` 只接受 Latin-1，中文/emoji 会抛异常或损坏。
3. base64：把字节按 8 位转字符再 `btoa`（或 `bytes → binary string → btoa`）。**只有这一次 base64，没有二次编码。**
4. 构造 `tEXt` chunk 并插到 `IEND` 之前：
   ```
   length(4, big-endian) = keyword.length + 1 + text.length
   type(4)   = "tEXt"
   data      = "chara" + 0x00 + <base64 字符串>
   crc(4)    = CRC32(type + data)
   ```
5. 如需 V3 兼容：再写一个 keyword = `ccv3` 的 `tEXt`，内容是 base64(UTF-8 的 V3 JSON)。**ST 的写入实现就是同时写 `chara` 和 `ccv3` 两个 chunk**（[character-card-parser.js `write()`](https://github.com/SillyTavern/SillyTavern/blob/HEAD/src/character-card-parser.js)，注意该文件头部注释说"只写 chara、移除 ccv3"，与代码行为不一致，以代码为准）。
6. 注意 `tEXt` 的 text 段按规范是 Latin-1；base64 正好是 ASCII，所以安全。想直接塞 UTF-8 中文必须用 `iTXt` chunk（生态不用这套）。

**读（导入 PNG 卡）**
1. 校验 8 字节 PNG magic：`89 50 4E 47 0D 0A 1A 0A`。
2. 从 offset 8 起顺序读 chunk：`length(4)` → `type(4)` → `data(length)` → `crc(4)`；遇到 `IEND` 停。
3. 取所有 `type === 'tEXt'` 的 chunk，按第一个 `0x00` 切成 keyword / text。
4. **keyword 大小写不敏感**地比较：先找 `ccv3`（V3 优先），再找 `chara`。
5. `text` 走 base64 解码 → **按 UTF-8 解码**（`new TextDecoder().decode(bytes)`，不要用 `atob` 直接当字符串，会乱码）→ `JSON.parse`。
6. `tEXt`/`iTXt` 之外还有 `zTXt`（压缩）——生态里基本不用；遇到可报"不支持"。

### 4.3 踩坑提醒
- ST 浏览器端 `extractDataFromPng()` 用**大小写敏感**的前缀比较匹配 `chara`（`x.data.slice(0, 5).every((v,i) => String.fromCharCode(v) == identifier[i])`），所以老卡若把关键字写成 `Chara` 会导入失败；服务端 `read()` 用的是 `keyword.toLowerCase() === 'chara'`。**我们实现时统一 `toLowerCase()` 比较**。
- ST 那个手写解析器读了 CRC 但**没有做校验**；写入时仍应算对 CRC，否则浏览器/图片库解码可能报错。
- WEBP 不被规范覆盖（V2 原文：`WEBP: Not covered by the spec due to technical ambiguities.`）。**不要试图兼容 webp 藏卡。**

## 5. 可借鉴清单：愿望机第一版数据结构（TypeScript 草案）

原则：**内部模型只保留"要用的"，其余一律进 `raw` / `extensions` 原样保留**，导出时再合并回去，保证「导入→导出」不丢字段（这是 V2/V3 规范都明写的 MUST NOT destroy）。

```ts
/* ---------- 角色卡：磁盘/网络上的原始形状（只用于导入导出） ---------- */
export type CardSpec = 'chara_card_v1' | 'chara_card_v2' | 'chara_card_v3' | 'unknown';

export interface RawCardV2 {
  spec: 'chara_card_v2';
  spec_version: '2.0';
  data: CardDataV2;
  [k: string]: unknown;          // 顶层 V1 镜像 + 未知字段，原样留
}

export interface CardDataV2 {
  name: string;
  description: string;
  personality: string;
  scenario: string;
  first_mes: string;
  mes_example: string;
  creator_notes: string;
  system_prompt: string;
  post_history_instructions: string;
  alternate_greetings: string[];
  character_book?: Lorebook;
  tags: string[];
  creator: string;
  character_version: string;
  extensions: Record<string, unknown>;   // 含 depth_prompt / world / talkativeness / fav
  // V3 字段：一版只"存"，不实现
  nickname?: string;
  assets?: unknown[];
  source?: string[];
  group_only_greetings?: string[];
  creator_notes_multilingual?: Record<string, string>;
  creation_date?: number;
  modification_date?: number;
}

/* ---------- 世界书 ---------- */
export interface Lorebook {
  name?: string;
  description?: string;
  scan_depth?: number;
  token_budget?: number;
  recursive_scanning?: boolean;
  extensions: Record<string, unknown>;
  entries: LorebookEntry[];
}

export interface LorebookEntry {
  keys: string[];               // spec 名；导入 ST 独立世界书时从 key 映射
  content: string;
  extensions: Record<string, unknown>;
  enabled: boolean;             // ST 的 disable 取反得到
  insertion_order: number;      // ST 的 order
  case_sensitive?: boolean;
  constant?: boolean;
  selective?: boolean;
  secondary_keys?: string[];
  position?: 'before_char' | 'after_char';
  name?: string;
  priority?: number;
  id?: number | string;
  comment?: string;
  use_regex?: boolean;          // V3，占位
  // —— 第一版实际会用到、但规范里没有的 ST 扩展（从 extensions 里提上来做运行时字段）——
  _depth?: number;              // extensions.depth，默认 4
  _role?: 0 | 1 | 2;            // extensions.role，system/user/assistant
  _probability?: number;        // extensions.probability，默认 100
  _matchWholeWords?: boolean;   // extensions.match_whole_words
  _selectiveLogic?: 0 | 1 | 2 | 3;

/* ---------- 愿望机自己的存储模型（IndexedDB 表） ---------- */
export interface WishCharacter {
  id: string;                   // 本地 uuid
  createdAt: number;
  updatedAt: number;
  spec: CardSpec;               // 导入时的来源规范

}

/* ---------- 会话 / 消息（可对齐 ST 的 .jsonl 语义） ---------- */
export interface WishChat {

```

## 6. 要避开的坑（每条带证据）

1. **`data` 与顶层镜像双份**。ST 导出的卡同时写 `char.first_mes` 和 `char.data.first_mes`（[characters.js:580-607](https://github.com/SillyTavern/SillyTavern/blob/HEAD/src/endpoints/characters.js)）。只读 `data` 会在遇到老 V1 卡时全空；只读顶层会在 V2 卡上拿到过期副本。**规则：`data` 优先，`data` 缺字段再回退顶层。**
2. **`chara` 关键字大小写**。规范 V1 写 "Chara"，ST 服务端 `toLowerCase()` 比较、浏览器端 `extractDataFromPng()` 大小写敏感比较。读的时候一律不敏感，写的时候一律小写 `chara`。
3. **`{{char}}` / `<BOT>` / `{{user}}` / `<USER>` 必须替换，且大小写不敏感**（V1 规范原文：`a case-insensitive search (e.g. <BOT> and <bot> both work)`）。`first_mes`、`mes_example`、`description`、`scenario` 里都可能有。必须有一个**默认用户名**（规范：`A default value for the user's name MUST exist`），否则开场白会出现空洞的 `{{user}}`。
4. **`mes_example` 靠 `<START>` 分块**。ST 的 `parseMesExamples()`：不以 `<START>` 开头就补一个；`openai`/instruct 模式下分隔符保留 `<START>\n`，文本补全模式下替换成 `example_separator`（默认 `***`）（[script.js `parseMesExamples`](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/script.js)）。不切分就会把整段示例当一条消息塞进去。
5. **同名不同形**：`keys`↔`key`、`secondary_keys`↔`keysecondary`、`insertion_order`↔`order`、`case_sensitive`↔`caseSensitive`、`enabled`↔**反向**的 `disable`（`disable:true` → `enabled:false`，见 [convertCharacterBook](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/world-info.js)）。把 ST 的数字 `position`（0–7）塞进规范的 `'before_char'|'after_char'` 字段会直接坏掉。
6. **ST 真实参数藏在 `extensions`**。`depth` / `probability` / `role` / `match_whole_words` / `useGroupScoring` / `sticky`… 在卡内是 `entry.extensions.*`，在独立世界书文件里却在**条目顶层**（见 `originalWIDataKeyMap`）。两套都要认。
7. **`entries` 是数组还是字典**要按文件形态判断：卡内 `character_book.entries` 是数组，ST 独立世界书是 `{uid: entry}` 字典；且 uid 在 JSON 里是**字符串键**。
8. **`creator_notes` / `tags` / `creator` / `character_version` MUST NOT 进 prompt**（V2 规范逐条写明）。把它们拼进 system prompt 是很常见的实现错误，白烧 token 还会污染人设。
9. **`system_prompt` / `post_history_instructions` 为空字符串时必须回退**到用户自己的设置，不能把空串当覆盖值；非空时要支持 `{{original}}` 占位符。
10. **`constant: true` 且 `use_regex: true`** 时 V3 要求忽略 `constant`；装饰器 `@@dont_activate` 会覆盖激活。
11. **`.jsonl` 头行不是消息**。第一行是 `{"chat_metadata":{}, "user_name":"unused", "character_name":"unused"}`（[chats.js:134-136](https://github.com/SillyTavern/SillyTavern/blob/HEAD/src/endpoints/chats.js)），没有 `mes`。按行无脑 map 会把头行变成一条空消息。
12. **swipe 结构不能只看 `mes`**。`mes` 是当前分支的副本，`swipes[]` 是全部候选，`swipe_id` 是下标，`swipe_info[i].extra` 与顶层 `extra` 是两套独立数据（[script.js:10345-10355](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/script.js)）。只存 `mes` 会静默丢掉用户的其他候补回复。
13. **导出时要跳过 `is_system: true` 的隐藏行**，ST 自己导出纯文本时就是这么做的（[chats.js](https://github.com/SillyTavern/SillyTavern/blob/HEAD/src/endpoints/chats.js)）。
14. **别按 UI 名称猜字段名**：界面上叫 "First message"，JSON 里是 `first_mes`；"Summary" 对应 `personality`；ST 内部还有个 `create_save.first_message` 只是表单字段名，不落盘。
15. **其他聊天格式的坑**（ST 的导入函数就是现成对照）：Ooba 的 `data_visible` 是 `[user, char]` **成对数组**；AgnAI 的 `messages[].userId` 用真假判断身份；Kobold Lite 用 `{{[INPUT]}}` / `{{[OUTPUT]}}` 标记（[chats.js](https://github.com/SillyTavern/SillyTavern/blob/HEAD/src/endpoints/chats.js)）。一版可以先只支持 `.jsonl`，但要按 `mes` 存在性做嗅探。
16. **`alternate_greetings` 是数组，不是字符串**；ST 专门写了兼容（接受 string 转成单元素数组）。`character_version` 是字符串，排序别 `parseInt`。
17. **V3 的 `nickname` 优先于 `name`** 用于 `{{char}}` 替换；不认识它就会用错名字。
18. **同时存在 `chara` 与 `ccv3` 两个 chunk 时以 `ccv3` 为准**（V3 规范与 ST `read()` 都是这个顺序）。

## 7. 提示词组装惯例（业界现状）

### 7.1 SillyTavern 默认的 Chat Completion 顺序（可直接照抄）
来自默认预设 [default/content/presets/openai/Default.json](https://github.com/SillyTavern/SillyTavern/blob/HEAD/default/content/presets/openai/Default.json) 的 `prompt_order`：

```
main                     ← 全局 system prompt（"Write {{char}}'s next reply in a fictional chat between {{char}} and {{user}}."）
worldInfoBefore          ← 世界书 position=before_char 的命中条目
charDescription          ← data.description
charPersonality          ← data.personality
scenario                 ← data.scenario
enhanceDefinitions       ← 默认关闭的"增强人设"提示
nsfw                     ← 空白的辅助提示位（Auxiliary Prompt）
worldInfoAfter           ← 世界书 position=after_char 的命中条目
dialogueExamples         ← mes_example 拆出来的示例对话
chatHistory              ← 真实历史（user/assistant 交替）
jailbreak                ← post_history_instructions（放在历史之后、生成之前）
```
（`personaDescription` 在 character_id=100001 的群聊顺序里插在 `worldInfoBefore` 之后。）

非 Chat Completion（文本补全/Kobold/Novel）走的是"story string"模板，默认值（[default/content/settings.json](https://github.com/SillyTavern/SillyTavern/blob/HEAD/default/content/settings.json) 的 `power_user.context.story_string`）：

```
{{#if system}}{{system}}\n{{/if}}{{#if wiBefore}}{{wiBefore}}\n{{/if}}{{#if description}}{{description}}\n{{/if}}{{#if personality}}{{char}}'s personality: {{personality}}\n{{/if}}{{#if scenario}}Scenario: {{scenario}}\n{{/if}}{{#if wiAfter}}{{wiAfter}}\n{{/if}}{{#if persona}}{{persona}}\n{{/if}}
```

### 7.2 实际效果更好 / 被吐槽的做法

**被验证有效的惯例**
- **人设在前、历史在中、越狱/收口指令在最后**。`chatHistory` 之后紧跟 `jailbreak`（post_history_instructions）是默认顺序；收口指令离生成点越近影响越大——这与世界书文档里"order 越大越靠后、影响越大"的口径一致。
- **世界书分前后两个槽位**：`before_char` 用来放世界观/设定（不太希望它压过角色），`after_char` 用来放"当前情境/状态"（更希望被模型重视）。文档原文：After Char Defs "has a greater impact"。
- **@Depth 注入**：把某些条目压到"聊天历史里的第 N 条"位置（Depth 0 = prompt 最底部），并以 system/user/assistant 三种角色之一出现。这是让设定"贴近"生成点又不破坏顶层结构的常用手法。
- **用说话人前缀做关键词扫描**（ST 的 Include Names 默认开）：扫的是 `Alice: 你好`，名字本身可以当触发词。
- **每条世界书条目的 `content` 必须自成一体**，因为 **key/comment/title 不进入上下文**（文档 Pro Tips 原文："Activation keywords, titles, and other information that is not in the Content field is not inserted into context"）。
- **constant 条目打底，其余按 order 排队**，预算耗尽即停。

**常见的吐槽点（我们不要重复）**
- **把 `creator_notes`/`tags`/`creator` 拼进 prompt**：规范明确禁止，纯烧 token。
- **`mes_example` 整段塞成一条 system**：示例本应是 user/assistant 交替的演示，整段塞进去会让模型把示例当"上一条对话"，进而复读示例内容。规范也要求示例在上下文不足时**优先被裁掉**给真实历史让位（V1 原文："Example conversations SHOULD, by default, only be included in the prompt until actual conversation fills up the context size, and then be pruned"）。
- **不给消息加角色名字前缀或到处乱加**：ST 把这件事做成显式开关 `names_behavior`（`NONE:-1 / DEFAULT:0 / COMPLETION:1 / CONTENT:2`，见 [openai.js:206-211](https://github.com/SillyTavern/SillyTavern/blob/HEAD/public/scripts/openai.js)），`DEFAULT` 只在群聊或带 `force_avatar` 时才加前缀。单聊里无脑加 `名字:` 既费 token 又容易让模型学着输出前缀。
- **世界书条目重复插入**：规范明写同一条命中多次**只插一次**（"The application MUST only add the content field once"）。
- **无脑递归触发导致上下文爆炸**：`recursive_scanning` 默认不推荐开；ST 文档也要求给预算/深度上限。
- **把 `{{user}}` 留成字面量**：模型会开始模仿 `{{user}}` 这个词，破坏输出格式。

### 8.3 给愿望机的具体建议

1. **不要把任何第三方角色卡随仓库或 APK 分发**。技术上卡是"数据"，但其中的文字（人设、开场白、世界书）在多数司法辖区受版权保护；平台 ToS 通常只授予**平台自己**托管/展示的权利，**不授予第三方再分发权**（这一点在没读到条款原文的前提下，按最保守处理）。
2. **第一版只做"导入器"**：用户在应用里粘贴 JSON / 选 PNG / 填 URL，卡存进用户自己的 IndexedDB。这是用户侧的个人使用行为，风险最低。要分发就分发**自己写的示例角色**，并明确标注许可（建议 CC0 或 CC BY 4.0，方便转载）。
3. **导入 PNG/JSON 时不做"卡内素材再分发"**：V3 的 `assets` 里可能是别人的立绘；本地显示可以，**不要**打进我们的包，也不要上传到我们的服务（我们本来也没有后端，这是天然优势）。
4. **保留 `creator` / `character_version` / `source` / `creator_notes`**：既是规范要求（creator_notes MUST 可发现地展示），也是署名礼貌；`source` 在 V3 里明确要求"只追加不修改"。
5. **NSFW 与未成年人风险另算**：这类站点存在大量成人内容与"疑似未成年外观"的角色卡，部分卡片还直接使用动漫/游戏 IP 角色。**上架 Google Play / App Store 前必须做内容分级与过滤**（Capacitor 打 APK 私下分发风险小，商店上架风险大）。建议第一版默认不内置任何卡、不内置任何图片素材、不提供在线卡库搜索。
6. **写明我们的许可**：愿望机自身建议 MIT 或 Apache-2.0（与生态工具链习惯一致）；在 README 里写明「导入的第三方角色卡版权归原作者，本项目不再分发」。
7. **不做"一键从 chub 下载"的网络请求**：一是 CORS/ToS 不确定，二是会让我们从"工具"变成"再分发方"。让用户自己贴 JSON/PNG。
