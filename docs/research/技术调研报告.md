# 「愿望机」纯前端零后端 AI 小手机 — 技术调研报告

> 调研时间：2026-10-30（UTC）｜调研方式：本机实测（curl 预检/CORS 探针）+ 官方文档 + 源码级核对 + 社区工单
> 凡标注「**未核实**」的，都是我没能拿到一手证据的，请不要当成结论使用。

---

## 1. 一句话结论

**能成，而且架构选型基本是对的。最大的拦路虎不是「有没有后端」，而是「CORS 这条命根子握在别人的服务器配置里」**——
我们自己没有服务器，就意味着**无法替用户兜底**：只要用户填的那个 API 地址不发 CORS 头，网页版就一点办法都没有（这是浏览器的硬边界，不是 bug）；Android APK 里可以用 `CapacitorHttp` 原生请求强行绕过 CORS，**代价是彻底失去流式输出（SSE）和请求取消能力**（有源码级证据，见 §6）。

所以第一版最该做的三个决定是：
1. **UI 层默认不做流式打字机，改成"拿到完整回复后本地逐字播放"**——这样 Web/APK 行为完全一致，且 APK 可以放心走原生请求兜底。
2. **设置页必须内置"连通性自检"**：一键发一个 1-token 的测试请求，把「CORS 失败 / 401 / 余额不足 / 网络不通」这四种错误用中文分别说清楚，并给出下一步建议（换中转站 / 开兼容模式）。
3. **必须做存档导出/导入（JSON 文件）**——iOS Safari 的 7 天存储清除策略会连带把 API Key 和聊天记录一起抹掉（见 §6.2）。

## 2. CORS 专项报告（最详细的一节）

### 2.1 结论速览

| 场景 | 浏览器 `fetch` 能不能通 | 证据 |
|---|---|---|
| 官方 `api.openai.com`（Chat Completions） | **能**（OpenAI 会回显 Origin） | 社区工单 + OpenAI 员工回复（§2.2） |
| 官方 `api.openai.com`（Responses API） | 2026-01-29 曾断了约 9 小时，现已修复 | 同上 |
| DeepSeek 官方 | **能**（回显 Origin，允许 `authorization,content-type`） | **本机实测 2026-10-30** |
| OpenRouter | **能**（`Access-Control-Allow-Origin: *`） | 本机实测 |
| SiliconFlow | **能**（`*`，允许所有头） | 本机实测 |
| 阿里 DashScope 兼容模式 | **能**（`*`） | 本机实测 |
| Moonshot 官方 | **能**（回显 Origin） | 本机实测 |
| 自建/中转站（one-api、new-api 系） | **默认能**（源码里 `AllowAllOrigins = true`） | 源码核对（§2.3） |
| 关闭了 CORS 的中转站 / 企业网关白名单 | **不能**，无解 | 浏览器标准行为 |
| **Capacitor WebView 里的 fetch** | **仍然受 CORS 限制**，和浏览器一模一样 | Ionic 官方员工回复 + 原生桥源码（§2.5） |
| **CapacitorHttp 原生请求** | **完全不受 CORS 限制** | 同上 |

**关键澄清：所谓「CORS 拦截」不是静默失败。** fetch 会 reject 出一个 `TypeError: Failed to fetch`，但**JS 层面拿不到原因**（真实原因只写在 DevTools 控制台），所以用户视角看起来就像"点了没反应"。我们的代码必须把 `TypeError` 统一翻译成中文提示。

### 2.2 OpenAI 官方接口到底怎么样

我在本机**无法实测** `api.openai.com`，因为这台机器的 DNS 被污染到了 Meta 的 IP（`getent hosts api.openai.com` → `2a03:2880:f131:83:face:b00c:0:25de`），用 Cloudflare DoH 查到的真实 IP（`162.159.140.245` / `172.66.0.243`）也连不通（TCP 层被阻断）。所以这一条**用社区一手证据**：

- OpenAI 官方论坛 **[Has the CORS policy changed (responses API)?](https://community.openai.com/t/has-the-cors-policy-changed-responses-api/1372791)**（2026-01-29）：
  - 用户 `_j` 的原话：**"Quite simply, Chat Completions has `access-control-allow-origin: null` in the OPTIONS response header, Responses does not."**（`null` 是因为他用 `file://` 打开的页面，Origin 就是 `null`，说明该接口是**回显 Origin** 的）
  - 多个 BYOK（用户自带 Key）纯前端应用当天集体挂掉：「All OpenAI requests that were previously succeeding began failing overnight due to CORS errors」
  - OpenAI 员工 `boxu` 回复：**"We have identified the issue and the fix has rolled out."**，用户确认恢复。
  - **这两个事实合起来说明：OpenAI 是「支持浏览器端带 Key 直连」的（否则不会当成 bug 来修），但这个支持随时可能因为一次发版而崩掉。**
- 同类工单：[How to Fix CORS Policy Error When Fetching OpenAI API from Localhost?](https://community.openai.com/t/how-to-fix-cors-policy-error-when-fetching-openai-api-from-localhost/1140420)（发帖人在中国大陆，前一天能用第二天不能用，典型是网络层被阻断后被 Chrome 报成 CORS 错）

> ⚠️ **要避开的认知坑**：Chrome 在**网络层连接失败**（DNS 污染、连接重置）时，控制台**也会**打印 "blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present"。所以中国用户报的"CORS 错误"，一半其实是**墙**，不是服务端配置。我们的自检逻辑要能区分（预检 OPTIONS 通不通 vs 主请求通不通）。

**给用户的自测方法（写进我们的文档/帮助页）**：在目标浏览器打开任意页面，控制台粘贴——

```js
// 探针 A：只看预检（不消耗 token、不泄露 Key）
fetch('https://api.openai.com/v1/chat/completions', {
  method: 'OPTIONS',
  headers: { 'Origin': location.origin },
}).then(r => console.log('preflight ok', r.status)).catch(e => console.log('preflight FAIL', e));
```
控制台出现红字 = 该地址在此网络环境下不可用。

### 2.3 中转站（这里是多数中国用户的实际入口）

国内绝大多数"中转站"是 **[one-api](https://github.com/songquanpeng/one-api)** 或 **[new-api](https://github.com/Calcium-Ion/new-api)** 搭的。我下载了两个仓库的源码直接核对：

`one-api/middleware/cors.go`：
```go
config := cors.DefaultConfig()
config.AllowAllOrigins = true
config.AllowCredentials = true
config.AllowMethods = []string{"GET", "POST", "PUT", "DELETE", "OPTIONS"}
config.AllowHeaders = []string{"*"}
```
`new-api/middleware/cors.go` 是同款实现。挂载位置：`router/relay.go` 里 `router.Use(middleware.CORS())`，即 **`/v1/chat/completions` 全系列默认全放行**。

**结论：只要是"自己搭 one-api/new-api"的中转站，浏览器直连默认是通的**，这大大提高了我们纯前端方案的可行率。风险在于：
- 有些站为了防白嫖会在 Cloudflare 上加 WAF 规则，可能把带 `Origin` 或空 `Origin` 的请求拦掉；
- 商业中转站可能改过 CORS（无法穷举，只能靠自检 + 兼容模式兜底）。

### 2.5 Capacitor 里的关键问题（决定架构的那一问）

**问题：Capacitor WebView 加载的页面发 fetch，受不受 CORS 限制？**
**答案：受，和浏览器完全相同。** 证据链有三条：

1. **Ionic 官方员工（twestrick）在官方论坛的原话**（[Does my API server need to CORS-allow capacitor://localhost?](https://forum.ionicframework.com/t/does-my-api-server-need-to-cors-allow-capacitor-localhost/250480)，2026-01）：
   > "If you are using the web stack to make your calls then you need the following origins for CORS on your backend server (these are Capacitor's defaults): **iOS: `capacitor://localhost`; Android: `http://localhost`; Android: `https://localhost`**. If you are using CapacitorHttp, then CORS doesn't apply as requests happen in native land outside of the browser."
2. **Capacitor 官方配置文档**：`server.androidScheme` 默认值已从 `http` 改成 **`https`**，所以 Capacitor 8 的 Android 应用 Origin 是 **`https://localhost`**（来源：[Config 文档](https://capacitorjs.com/docs/config)，`androidScheme` 的 `@default https`）。
3. **源码**：`android/capacitor/src/main/assets/native-bridge.js` 里能直接看到 `window.fetch` 被替换的逻辑，以及 GET/HEAD 走 `createProxyUrl()` 本地代理、POST 走 `cap.nativePromise('CapacitorHttp','request')` 的分支。

**推论（对我们特别重要）**：
- Android APK 的 Origin 是 `https://localhost`。**回显 Origin 的服务（OpenAI、DeepSeek、Moonshot）和 `*` 的服务（OpenRouter、SiliconFlow、DashScope）在 APK 里都能正常直连**，跟网页版没区别。
- 只有"白名单式"服务端才需要额外加 `https://localhost` / `capacitor://localhost`，现实中几乎没人这么配——所以**APK 并不比网页版更宽松**，不要幻想"套壳就能解决 CORS"。

**CapacitorHttp 怎么用、和标准 fetch 差在哪：**

官方文档（[Http Capacitor Plugin API](https://capacitorjs.com/docs/apis/http)）原文：
> "The Capacitor Http API provides native http support via patching `fetch` and `XMLHttpRequest` to use native libraries. **This plugin is bundled with `@capacitor/core`.**"
> "**By default, the patching of `window.fetch` and `XMLHttpRequest` to use native libraries is disabled.**"

开启方式（`capacitor.config.ts`）：
```ts
import type { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'app.wishphone',
  appName: '愿望机',
  webDir: 'dist',
  server: { androidScheme: 'https' },          // 默认已是 https
  plugins: {
    CapacitorHttp: { enabled: true },          // 开启后 window.fetch / XHR 被替换为原生请求
  },
};
export default config;
```

改动对比（重要，别踩）：

| 维度 | 标准 `fetch`（WebView 网络栈） | `CapacitorHttp.request()` / 开启 patch 后的 `fetch` |
|---|---|---|
| CORS | **受限** | **不受限**（原生 OkHttp/HttpURLConnection 发请求） |
| 流式 SSE | 支持（`response.body.getReader()`） | **不支持**，响应被整体缓冲后 `new Response(text)`（证据见 §6.1） |
| `AbortController` 取消 | 支持 | **不生效**，patch 代码完全没有读 `options.signal` |
| 超时 | 由浏览器决定 | 走原生，**默认不设超时**（近乎无限等待），需要显式传 `connectTimeout/readTimeout` |
| 请求头 | 带 `Origin` | Android 上**不带 Origin**（社区实测为 undefined），部分服务端/风控会因此拒绝 |
| 延迟 | 低 | 高一层（web↔native 序列化/反序列化），官方人员原话："adds some latency" |
| 复杂 body（FormData/Blob） | 支持 | 需手动转 base64 + `dataType` |

Ionic 官方人员的定位也说得很清楚（[CapacitorHttp on Android is sending empty origin](https://forum.ionicframework.com/t/capacitorhttp-on-android-is-sending-empty-origin/247643)）：
> "CapacitorHttp was created primarily to get around CORS issues when making requests to 3rd party APIs that don't allow requests from localhost and **this is the last resort**."

**所以我们的架构决策是：`CapacitorHttp` 定位为「兼容模式开关」，而不是默认开启。**

### 2.6 业界纯前端项目的真实方案对比

| 方案 | 怎么做 | 优点 | 缺点 | 我们对它的取舍 |
|---|---|---|---|---|
| **A. 让用户自备支持 CORS 的接口** | 自检 + 文档引导（推荐官方 API / one-api 自建站） | 零成本、零中间人、隐私最好 | 部分中转站不通；用户认知门槛 | ✅ **默认路线** |
| **B. 引导用户自部署转发（CF Worker / Vercel Function）** | 给一份 20 行的 Cloudflare Worker 模板，一键部署 | 100% 解决 CORS | 与"零后端"的产品叙事冲突；用户要多注册一个账号 | ⚠️ **作为"高级文档"提供，不作为主路径** |
| **C. Capacitor `CapacitorHttp` 原生请求** | 见上 | APK 内彻底解决 CORS | 丢流式、丢取消、无超时、多一层延迟 | ✅ **APK 内做"兼容模式"兜底** |
| **D. 浏览器扩展** | 用 `declarativeNetRequest` 改响应头 | 能改 CORS | 只对装扩展的桌面用户有效；移动端无解 | ❌ 不做 |
| **E. 公共 CORS 代理（allorigins 之类）** | 请求别人搭的转发 | 零配置 | **等于把用户的 API Key 送给第三方**，随时挂掉 | ❌ **明令禁止** |
| **F. 本地小代理（用户自己跑 `npx wishphone-proxy`）** | 本地起服务转发 | 解决 CORS | 违背"点链接即用"；手机端无法用 | ❌ 不做 |
| **G. `no-cors` 模式** | — | — | 拿不到响应体，**对这个需求毫无意义** | ❌ |

**推荐组合：A（默认）+ C（APK 内一键切换）+ B（文档里的逃生舱）。**

### 2.7 API Key 存在前端的风险，以及更安全的做法

**官方怎么说**（[Capacitor Security Best Practices](https://capacitorjs.com/docs/guides/security)）：
> "One of the most important security tips for Capacitor apps ... is to **never embed secrets in your app code** ... Instead, **move most operations requiring secret keys or tokens to the server-side**."
> "For apps that must work with persisted sensitive keys or tokens on the client ... the recommended options are to only deal with the value in memory (i.e. never persist it to disk), or by using **secure keychain/keystore techniques** ... available in the **iOS Keychain Services** and **Android Keystore APIs** ... you will likely want to find a plugin that uses them for you."

OpenAI 官方 SDK 的态度可以当行业注脚（[openai-node README](https://github.com/openai/openai-node)）：
> "Web browsers: **disabled by default to avoid exposing your secret API credentials.** Enable browser support by explicitly setting `dangerouslyAllowBrowser` to `true`."

**但对我们的产品，这个风险是「可接受的、且必须如实告知的」**：用户填的是**自己的** Key，存在**自己的**设备上，我们的代码里没有 Key，也没有我们的服务器去收 Key。这和"开发者把 Key 打包进 App 发给所有人"是两回事。真正要防的是：

| 威胁 | 现实性 | 我们的对策 |
|---|---|---|
| 我们自己的站点被 XSS → 偷 localStorage/IndexedDB | 中（纯前端 + 无用户输入 HTML 渲染可降到低） | 严格 CSP、不 `innerHTML` 渲染模型输出、Markdown 用白名单渲染器 |
| 用户在公共/二手手机上使用 | 中 | 提供"清除全部数据"按钮；APK 版存 Keychain/Keystore |
| 恶意浏览器扩展读取页面存储 | 低-中 | 无法防，文档里说明 |
| 共享设备上他人打开浏览器 | 中 | 提供"每次启动要 PIN"（后期） |

**更安全的做法（按性价比排序）**：
1. **Android/iOS 套壳版**：用原生安全存储插件存 Key（不在 WebView 存储里）。候选（均为社区插件，npm 元数据核对于 2026-10-30）：
   - [`@aparajita/capacitor-secure-storage`](https://www.npmjs.com/package/@aparajita/capacitor-secure-storage) `8.0.1`｜MIT｜最后更新 2026-09-23｜明确写 "Capacitor 8+ / iOS Keychain + Android Keystore" ✅ 首选
   - [`capacitor-secure-storage-plugin`](https://www.npmjs.com/package/capacitor-secure-storage-plugin) `0.13.0`｜MIT｜最后更新 2026-01-10｜老牌，用户最多
   - Capacitor 官方的 [`@capacitor/preferences`](https://www.npmjs.com/package/@capacitor/preferences) `8.0.1`｜MIT｜**不是加密存储**（Android SharedPreferences / iOS UserDefaults），只能算"放到原生侧"，别当保险箱
2. **网页版**：Key 只放 IndexedDB，但**明文**。可选：用 `crypto.subtle` 派生密钥做一层混淆（**只能防"肉眼看到"，防不住 XSS**，别在 UI 里吹成"加密"）。
3. **永远不要把 Key 塞进 URL query**（会进浏览器历史、Referer、日志）。统一放 `Authorization` 头。
4. **页面上给一次性的风险提示**：第一次填 Key 时明确写"Key 只存在这台设备的浏览器里，我们看不到；请勿在公共电脑上使用"。

## 3. Capacitor 打包链路（可照做）

### 3.1 一次性准备（本地）

Capacitor 8 的环境要求（[官方 Environment Setup](https://capacitorjs.com/docs/getting-started/environment-setup)）：
- **Android Studio 2025.2.1+**（官方只要求这个，JDK 由它自带）
- **Android SDK**，API 24 以上的 Platform（当前最新稳定 Android 16 / API 36）
- 纯命令行用户可以不装 Android Studio，只装 SDK command-line tools —— **CI 里完全不需要 Android Studio**（见 §3.3）

Capacitor 8 的 Android 工程基线（我直接读的源码 `android-template/`）：

| 项 | 值 | 来源 |
|---|---|---|
| `minSdkVersion` | 24 | `android-template/variables.gradle` |
| `compileSdkVersion` / `targetSdkVersion` | 36 / 36 | 同上 |
| Android Gradle Plugin | `8.13.0` | `android-template/build.gradle` |
| Gradle Wrapper | `8.14.3` | `gradle/wrapper/gradle-wrapper.properties` |
| Java 源/目标版本 | **21** | `android/capacitor/build.gradle`（`JavaVersion.VERSION_21`） |

### 3.2 从 Vite 项目到 APK 的完整步骤

```bash
# ① 建 Vite 项目
npm create vite@latest wish-phone -- --template vanilla-ts
cd wish-phone && npm install

# ② 装 Capacitor（core+cli 是必须的，android 是平台包）
npm i @capacitor/core@^8.6.0
npm i -D @capacitor/cli@^8.6.0
npm i @capacitor/android@^8.6.0

# ③ 初始化配置（生成 capacitor.config.ts）
npx cap init 愿望机 app.wishphone --web-dir dist
#    注意：appId 必须是反向域名格式，且一旦上架不要改

# ④ 构建 Web 产物
npm run build                 # → dist/

# ⑤ 添加 Android 平台（只做一次；会生成 android/ 目录，必须提交进 Git）
npx cap add android

# ⑥ 每次改完 Web 代码：构建 + 同步
npm run build && npx cap sync android
#    (sync = copy web 产物 + 更新原生依赖 + 生成 capacitor.build.gradle)

# ⑦ 出 APK（纯命令行，不需要 Android Studio）
cd android
./gradlew assembleDebug       # Debug APK
./gradlew assembleRelease     # Release APK（需先配签名）
#  产物路径：
#   android/app/build/outputs/apk/debug/app-debug.apk
#   android/app/build/outputs/apk/release/app-release-unsigned.apk (未签名时)
#   AAB: android/app/build/outputs/bundle/release/app-release.aab
```

> ⚠️ **`android/` 目录必须提交进 Git**。Capacitor 的原生工程是"源码"不是"构建产物"，CI 里的 `npx cap sync android` 依赖它的存在。另外**签名的 keystore 绝对不能进 Git**。

### 3.3 可直接使用的 GitHub Actions Workflow

设计要点：
- **不需要 Android Studio、不需要手动装 SDK**：GitHub 官方的 `ubuntu-24.04` 镜像**已预装 Android SDK**（`ANDROID_HOME=/usr/local/lib/android/sdk`，含 build-tools 36.x 与 `android-36` platform，见 [runner-images Ubuntu2404-Readme.md](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md)）与 **JDK 21**（`JAVA_HOME_21_X64`）。
- **JDK 必须是 21**（Capacitor 8 的 Android 库以 Java 21 编译）。
- 版本号：以下 action 主版本号我都在 2026-10-30 通过 GitHub API **实测存在**（`GET /repos/:owner/:repo/git/ref/tags/:tag` 全部返回 200）：`actions/checkout@v7`、`actions/setup-node@v7`、`actions/setup-java@v6`、`actions/upload-artifact@v7`、`android-actions/setup-android@v4`、`actions/cache@v4`。**若某天 CI 报 `unable to resolve action`，把该 action 降一个大版本即可**（例如 `@v7` → `@v4`）。

```yaml
# .github/workflows/android.yml
name: Build Android APK

on:
  push:
    branches: [main]
    tags: ['v*']
  workflow_dispatch:

permissions:
  contents: read

jobs:
  android:
    name: Build APK
    runs-on: ubuntu-24.04
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Setup Node
        uses: actions/setup-node@v7
        with:
          node-version: '22'        # Vite 8 要求 ^20.19 || >=22.12
          cache: npm

      - name: Setup JDK 21
        uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '21'

      - name: Cache Gradle
        uses: actions/cache@v4
        with:
          path: |
            ~/.gradle/caches
            ~/.gradle/wrapper
          key: gradle-${{ runner.os }}-${{ hashFiles('android/**/*.gradle*', 'android/gradle/wrapper/gradle-wrapper.properties') }}
          restore-keys: gradle-${{ runner.os }}-

      - name: Install web deps
        run: npm ci

      - name: Build web assets
        run: npm run build

      - name: Sync Capacitor Android
        run: npx cap sync android

      # ---------- Debug APK（永远能出，用于内测分发） ----------
      - name: Build Debug APK
        working-directory: android
        run: |
          chmod +x ./gradlew
          ./gradlew assembleDebug --no-daemon --stacktrace

      - name: Upload Debug APK
        uses: actions/upload-artifact@v7
        with:
          name: wishphone-debug-apk
          path: android/app/build/outputs/apk/debug/app-debug.apk
          if-no-files-found: error
          retention-days: 14      # ⚠️ 存太久会吃掉你的 artifact 存储额度（Free 只有 500MB）

      # ---------- Release APK（打 tag 时构建，需在仓库 Secrets 里配好 keystore） ----------
      - name: Decode keystore
        if: startsWith(github.ref, 'refs/tags/v')
        env:
          KEYSTORE_BASE64: ${{ secrets.ANDROID_KEYSTORE_BASE64 }}
        run: |
          echo "$KEYSTORE_BASE64" | base64 -d > android/app/release.keystore

      - name: Build Release APK
        if: startsWith(github.ref, 'refs/tags/v')
        working-directory: android
        env:
          KEYSTORE_PATH: ${{ github.workspace }}/android/app/release.keystore
          KEYSTORE_PASSWORD: ${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
          KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
          KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
        run: ./gradlew assembleRelease --no-daemon --stacktrace

      - name: Upload Release APK
        if: startsWith(github.ref, 'refs/tags/v')
        uses: actions/upload-artifact@v7
        with:
          name: wishphone-release-apk
          path: android/app/build/outputs/apk/release/app-release.apk
          if-no-files-found: error
          retention-days: 14
```

配套的 `android/app/build.gradle` 签名片段（在 `android { }` 内加 `signingConfigs`，并把 `buildTypes.release` 指过去）：


### 3.4 开源项目发 APK 的常见做法

| 问题 | 结论 |
|---|---|
| **Debug 签名能直接发给用户吗？** | **技术上能，且是 F-Droid/开源项目的常见做法**（GitHub Releases 里挂 `app-debug.apk`）。Debug 签名用的是公共的 debug keystore，**任何人拿到你的 debug key 都能签出"同一个应用"**，所以**不能上架、不能用于任何需要身份保证的场景**，用户手动安装时 Android 也可能提示风险。**建议：内测阶段发 debug APK，对外正式发布一定用 release 签名。** |
| **Release keystore 怎么保管** | ① keystore 文件 + 口令分两处存（口令放 GitHub Secrets，文件本身也可以 base64 进 Secrets，如上面的 workflow）；② 本地/离线再留一份备份（丢了无法升级同包名应用）；③ **绝不提交进 Git**；④ 用 CI 的环境变量注入，不要硬编码在 `build.gradle`。 |
| **APK 体积** | **未核实**（我没有实测出一个裸 Vite+Capacitor 8 项目的 APK 大小）。可参考的社区案例：[Capacitor app size compared to Cordova](https://forum.ionicframework.com/t/capacitor-app-size-compared-to-cordova/213063) 里，一个 Ionic+Angular 应用从 Cordova 的 12MB 涨到 Capacitor 3 的 22MB（**那是含 Angular 全套依赖的应用，不是我们这个量级**）。我们这个「无框架 + 无重型插件」的项目，Web 产物应该在 200~500KB 量级，APK 主体是 Capacitor/AndroidX 的原生开销，**我预计在个位数 MB，但请以第一次 CI 构建的真实数字为准**（用 `bundleRelease` + AAB 更小）。你可以顺便在 workflow 里加一行 `ls -la android/app/build/outputs/apk/*/*.apk` 记录体积。 |

### 3.5 GitHub Actions 在公开仓库的免费额度与陷阱

官方文档（[GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)）原文：
> "The use of standard GitHub-hosted runners is free: **In public repositories** / For GitHub Pages / For Dependabot."
> "Larger runners are billed for public repositories." ← **大规格 runner 在公开仓库不免费**

**额度陷阱（都是真金白银的坑）**：
1. **计算免费 ≠ 存储免费**！GitHub Free 的 artifact 存储只有 **500MB**（Pro 1GB / Team 2GB / Enterprise Cloud 50GB），**并且和 GitHub Packages 共享额度**。我们一个 APK 几 MB，retention 默认 90 天，每天构建几个 tag 很容易把 500MB 吃满 → 一定设 `retention-days: 14` 并定期清旧 artifact。
2. **`ubuntu-latest` 会漂移**。它当前指向 24.04，将来会切到 26.04（26.04 镜像的**默认 JDK 是 25**，对我们是个隐患）。所以上面我**写死 `ubuntu-24.04`**，别用 `latest`。
3. **不要用 `macos-*` runner 构建 Android**：public repo 上 macOS runner 也是免费的，但没用且更慢；**另外注意 macOS runner 对 public repo 虽免费，但如果你以后把仓库转私有，账单会突然出现**。
4. **Gradle 首次构建很慢**（要下 `gradle-8.14.3-all.zip` 约 200MB + 全部 Maven 依赖），一定要开 `actions/cache`，否则每次 8~15 分钟。
5. 公开仓库的 Actions 日志人人可见：**不要把 Key、keystore 口令 echo 到日志里**。

## 4. 工程选型对比表

### 4.1 IndexedDB 封装

体积数据为**我本机实测**（`gzip -9` 后的字节数，2026-10-30）：

| 方案 | 版本 | 体积（原/压缩） | 学习成本 | TS 友好度 | 推荐 |
|---|---|---|---|---|---|
| 原生 IndexedDB | — | 0 | **高**（事务生命周期、回调地狱、`onupgradeneeded` 易错） | 差（`IDBRequest` 类型繁琐） | ❌ 不推荐直接用 |
| **`idb`** | 8.0.4 | **11.6KB / 3.4KB** | **低**（就是 Promise 化的原生 API） | **极好**（`DBSchema` 泛型约束全链路） | ✅ **强烈推荐** |
| `dexie` | 4.4.7 | 96.3KB / 30.8KB | 低（API 最像 SQL/ORM） | 好（泛型支持完善） | ⚠️ 功能过剩，除非要 `liveQuery` |
| `localforage` | — | — | 低 | 一般 | ❌ 太老，类型差 |

**结论：用 `idb`（ISC 许可）。** 理由：我们的需求只有「几个对象仓库 + 简单查询」，`idb` 只做一层薄薄的 Promise 包装，**3.4KB gzip 的成本换来完全的类型安全**，而且它不隐藏 IndexedDB 的语义（对"便于零基础用户维护"这个目标是加分项）。Dexie 的 30.8KB 和多一层抽象，在我们要"坑少"的诉求下反而是负担。

### 4.2 状态管理（原生 DOM 下）

| 方案 | 体积 | 学习成本 | TS 友好度 | 推荐 |
|---|---|---|---|---|
| **手写极简 store（~40 行）** | 0 | 低（但得自己写对） | 好 | ✅ **推荐**（MVP 够用） |
| `nanostores` | 54KB unpacked（实际产物极小，**未实测 gzip**） | 极低 | 好 | ⚠️ 备选 |
| `zustand` | 94KB unpacked | 低 | 好 | ❌ 为 React 而生，原生 DOM 下浪费 |
| Redux / MobX | 大 | 高 | 中 | ❌ |

**推荐形态**（够用且不引依赖）：
```ts
// src/core/store.ts
type Listener<T> = (s: T) => void;
export function createStore<T extends object>(initial: T) {
  let state = initial;
  const listeners = new Set<Listener<T>>();
  return {
    get: () => state,
    set(patch: Partial<T>) { state = { ...state, ...patch }; listeners.forEach(l => l(state)); },
    subscribe(l: Listener<T>) { listeners.add(l); return () => listeners.delete(l); },
  };
}
```
配合「每个屏幕一个 render 函数，`subscribe` 里只重渲染"脏"的那一块 DOM」，不要整页 `innerHTML = ...`。**这一条比选哪个库重要 10 倍**：整页重绘会毁掉我们的果冻动画（动画中的元素被替换 → 动画中断、焦点丢失、输入法弹回）。

### 4.4 Vite + TS 移动端 PWA 的目录结构建议

**核心思想：按"功能/屏幕"切，不按"技术层"切**（`components/`、`services/` 这种分法在 2 万行的项目里会迅速失控）。

```
wish-phone/
├─ index.html
├─ public/
│  ├─ manifest.webmanifest
│  └─ icons/                 # 192/512/maskable/apple-touch-icon
├─ src/
│  ├─ main.ts                # 唯一入口：启动、路由注册、全局错误兜底
│  ├─ app.css                # 设计令牌（CSS 变量）+ 全局重置
│  ├─ core/                  # 与 UI 无关的地基，谁都能依赖它，它不依赖任何人
│  │  ├─ store.ts            # 极简 store
│  │  ├─ db.ts               # idb：schema、迁移、CRUD
│  │  ├─ router.ts           # hash 路由（见 §6.4 为什么不用 History API）
│  │  ├─ i18n.ts             # 或先硬编码中文
│  │  └─ dom.ts              # el()/on()/mount() 这类 DOM 小工具
│  ├─ ai/                    # AI 调用层：整个项目最危险的地方，必须独立
│  │  ├─ types.ts            # 统一的 ChatMessage / ChatOptions
│  │  ├─ client.ts           # fetch / CapacitorHttp 双通道 + 超时 + 取消
│  │  ├─ sse.ts              # 流式解析（可选）
│  │  └─ errors.ts           # 把 TypeError/401/429 翻译成中文人话
│  ├─ features/              # 一个屏幕一个目录，内部自带 ui + logic
│  │  ├─ desktop/            # 桌面：时钟、日期、图标网格
│  │  ├─ chat/               # 聊天
│  │  ├─ character/          # 角色系统
│  │  └─ settings/           # API 设置、自检、导出/导入
│  ├─ ui/                    # 跨屏幕复用的视觉原子
│  │  ├─ button.ts           # 果冻回弹按钮
│  │  ├─ sheet.ts            # 底部弹层
│  │  └─ icons.ts            # 只导出用到的那几个图标
│  └─ types/                 # 全局类型
├─ android/                  # Capacitor 原生工程（提交进 Git）
├─ capacitor.config.ts
├─ vite.config.ts
└─ tsconfig.json
```

**模块边界铁律**：
1. `core/` 和 `ai/` **不许 import 任何 UI 代码**（这样将来换 UI 不用重写业务）。
2. `ai/client.ts` 是**唯一**可以直接发 HTTP 的地方，其余代码只能调它（将来加"兼容模式"只改一个文件）。
3. `features/*` 之间**不许互相 import**，共享的东西必须下沉到 `core/` 或 `ui/`。这条规则用 ESLint 的 `import/no-restricted-paths` 强制，比口头约定可靠。

**中文 Web 字体的体积问题与子集化方案（这是必须解决的问题，不是可选项）**：
- 一个完整中文字体有 2~3 万字形，**不可能整包发**。三条路：
  1. **零字体方案（推荐 MVP 用）**：CSS 直接写
     ```css
     font-family: system-ui, -apple-system, "PingFang SC", "HarmonyOS Sans SC",
                  "Noto Sans CJK SC", "Microsoft YaHei", sans-serif;
     ```
     体积 0，各平台都用系统最优中文字体（iOS 苹方 / 鸿蒙 HarmonyOS Sans / 安卓思源）。**缺点是跨设备视觉不一致**。
  2. **按 `unicode-range` 分片**（用 `@fontsource-variable/noto-sans-sc`，4.87MB 总量但首屏只下几片）——工作量 0，成本可控，**推荐第一版就用这个做 UI 主字体**。
  3. **精确子集化**（只保留我们 UI 文案里出现的字）：工具用 **[`cn-font-split`](https://www.npmjs.com/package/cn-font-split) 7.4.3（Apache-2.0）** 或 Python 的 `fonttools pyftsubset`。UI 固定文案 300~800 字 → **woff2 通常能压到 60~150KB**。代价是：用户输入的内容、模型输出的生僻字会 fallback 到系统字体（**这其实完全可接受**，因为正文本来就是"用户和 AI 说的话"，字形不一致反而无所谓；把子集化只用在**界面控件文案**上）。
- **数字好看的关键**：时间/日期/数字用 `font-variant-numeric: tabular-nums;`（让数字等宽，时钟跳动时不会左右抖），配 `JetBrains Mono` 或 `Noto Sans Mono` 做 fallback。

### 5.3 有没有现成的"手机桌面"组件库

**结论：没有值得用的，自己写更省事。** 理由：
- Ionic Framework / Framework7 / Onsen UI 这些都**自带一整套视觉语言和路由**，与"Vite + 原生 DOM、黑白灰极简、果冻回弹"三个约束直接冲突，引进来会变成"和框架打架"。
- 我们要的"手机桌面"（图标网格 + Dock + 状态栏 + 弹层）本来就是**几十行 CSS Grid** 的事。
- 唯一值得抄的是**设计令牌**：颜色（`#000/#111/#333/#888/#eee/#fff` + 一档灰阶）、圆角（12/18/24px）、间距（4px 基准）、阴影（几乎不用，用 1px `#222` 描边替代）。抄 Apple HIG 的**间距与触控区尺寸**（最小点击区 44×44pt）即可。

### 5.4 果冻回弹动画的移动端性能注意点

**（1）只动 `transform` 和 `opacity`。**
MDN（[Animation performance and frame rate](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Animation_performance_and_frame_rate)）的解释：改一个属性会走完整条渲染瀑布——
> "Properties that affect an element's geometry or position trigger a: style recalculation / layout / repaint. For example: `left`, `max-width`, `border-width`, `margin`"

也就是说：**按压缩放必须用 `transform: scale()`，绝不能改 `width/height/margin/top/left`**，否则每一帧都要重排（我们按下的那个瞬间正好是用户最敏感的 100ms）。

**（2）`will-change` 要用对，不是常开。**
MDN（[will-change](https://developer.mozilla.org/en-US/docs/Web/CSS/will-change)）示例给的就是"在需要时用 JS 加、用完移除"：
```js
el.addEventListener("pointerdown", () => { el.style.willChange = "transform, opacity"; });
el.addEventListener("animationend", () => { el.style.willChange = "auto"; });
```
**常开 `will-change: transform` 反而是坑**：每个元素都提升为独立合成层 → 显存暴涨 → 低端安卓机（GPU 内存本来就少）出现掉帧甚至整机卡顿。**桌面图标有几十个，绝对不要给所有图标常开 `will-change`。**

**（3）给动画的曲线和时长（按你给的要求）**：
```css
:root {
  --ease-jelly: cubic-bezier(0.34, 1.56, 0.64, 1); /* 带过冲 */
}
.pressable {
  transition: transform 0.7s var(--ease-jelly);
  touch-action: manipulation;          /* 去掉 300ms 点击延迟与双击缩放 */
  -webkit-tap-highlight-color: transparent;
}
/* 按下用极短的线性快压（不要用弹簧曲线，否则"按不动"） */
.pressable:active {
  transform: scale(0.94);
  transition: transform 0.07s linear;
}
```
**（4）低端机与细节坑**：
- **别用 `transition: all`**——会把 `color`、`box-shadow` 之类也拖进来逐帧计算。
- **松手后的回弹要允许被打断**：用户连点两下时，第二下的 `pointerdown` 必须能立刻覆盖正在进行的回弹（CSS transition 天然支持，但如果你在 JS 里用 `requestAnimationFrame` 手写动画就必须自己处理打断）。
- **`animation` vs `transition`**：果冻回弹只需 `transition` + `:active`，不需要 `@keyframes`，**越简单越不容易掉帧**。
- **`prefers-reduced-motion`**：无障碍上应该降级为无动画（系统开了"减弱动态效果"的用户，过冲动画会引起不适）。
- **WebView 里 `:active` 在滚动中会误触发**，所以按下效果最好用 `pointerdown/pointerup` + `touch-action`，并且滚动容器上不要挂 `:active` 样式。

## 6. 要避开的坑（带证据）

### 6.1 ⛔ 最大坑：以为"套壳 APK 就能解决 CORS + 还能继续流式输出"

**这两个需求在 Capacitor 里是互斥的。**

**证据 1：CapacitorHttp 没有流式支持，且官方明确不会做。** [ionic-team/capacitor#6582 "CapacitorHttp - No support for Server-Sent Events"](https://github.com/ionic-team/capacitor/issues/6582)（2023-05 开，2026-04 被官方按"backlog cleanup"流程自动关闭，**功能未实现**）：
> "I tried to use fetch-event-source to get a `fetch()` based approach for `text/event-stream`, but even that isn't good enough, **since the patched fetch can't seem to stream data**."
> "I'd like to kindly request the Ionic team to consider adding support for the `text/event-stream` response type. This would greatly benefit scenarios like **integrating OpenAI's chat completion with streaming, which is currently not achievable using the Capacitor's HTTP module**."

**证据 2（源码级，我自己读的）**：`android/capacitor/src/main/assets/native-bridge.js` 中 patch 后的 fetch：
```js
const nativeResponse = await cap.nativePromise('CapacitorHttp', 'request', { url, method, data, dataType, headers });
// ... 响应被整体拿到后，才构造 Response：
const response = new Response(data, { headers: nativeResponse.headers, status: nativeResponse.status });
```
**它是"等整个响应收完 → 拼成一个完整字符串 → 造一个假 Response"**。`response.body` 是一次性的完整内容，**没有流**。

**证据 3（源码级）：patch 后的 fetch 完全忽略 `AbortController`。** 同一文件里 grep 不到任何 `signal` 处理（`abort` 只出现在 XHR 分支，而且那个 abort 是假的：`prototype.abort` 只发了个 `abort` 事件，**没有真的取消原生请求**）。后果：**"停止生成"按钮会变成摆设**，而且**没有超时**——native 调用不传 `connectTimeout/readTimeout`，Android `HttpURLConnection` 默认是 0（无限等待）。用户网络一抽风，界面就永远转圈。

**结论与对策**：
- MVP **默认走非流式**：`stream: false`，拿到完整回复后用 `setInterval`/`requestAnimationFrame` **本地逐字播放**（体验上 90% 场景无差别，还能顺便支持"暂停/重播"）。
- 如果一定要流式：**只在 Web 端 / 未开启 patch 的 APK 里走 `fetch` 流式**，并且**必须有非流式兜底**。
- 请求层写成策略模式：`AiClient.send()` → 依次尝试 `streamFetch` → `plainFetch` → `CapacitorHttp`，每一层把自己的失败原因翻译成人话给用户看。

### 6.2 ⛔ iOS 会悄悄删掉用户的存档和 API Key

**证据**（WebKit 官方博客 [Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)）：
> "deleting all of a website's script-writable storage **after seven days of Safari use without user interaction on the site**. These are the script-writable storage forms affected: **Indexed DB, LocalStorage, ... Service Worker registrations and cache**"
> "**A Note On Web Applications Added to the Home Screen**: ... Web applications added to the home screen are not part of Safari and thus have their own counter of days of use. ... **We do not expect the first-party in such a web application to have its website data deleted.**"

**解读**：**只用 Safari 打开（不安装到主屏）的 iOS 用户，只要 7 天没点开这个站点，IndexedDB 里的聊天记录和 API Key 全部蒸发。** 安装到主屏可以规避。

**对策（都要做）**：
1. 首屏就调 `navigator.storage.persist()`（WebKit 10218 明确说它"基于启发式授予，例如网站是否作为主屏 Web App 打开"）。
2. 检测到 iOS 且未安装时，**主动弹一次引导**："在 iPhone 上请点分享 → 添加到主屏幕，否则 7 天不使用记录会消失"。
3. **必须提供导出/导入 JSON**（这也是"纯本地数据"产品的基本素养）。⚠️ **注意**：iOS 独立 PWA 里的 `<a download>` 行为在多版本上有过问题（**未核实**当前版本），建议导出优先用 **Web Share API**（`navigator.share({files})`），失败再回退到 blob 下载。
4. 存档写入时机不要只在 `beforeunload`（移动端不可靠），要**写完一条消息就落库**。

### 6.3 ⛔ 把 `CapacitorHttp.enabled = true` 全局打开

它是**全局替换 `window.fetch`**。一旦开启：
- 你自己的静态资源、`import()`、图片、Analytics 假如用了 fetch，**全都走原生**（多一层序列化，且行为差异一堆）；
- 所有 SSE 全废（见 6.1）；
- Android 上请求**不带 Origin**，部分中转站/Cloudflare 风控会因此 403（社区实测：[CapacitorHttp on Android is sending empty origin](https://forum.ionicframework.com/t/capacitorhttp-on-android-is-sending-empty-origin/247643)）。
**正确做法：不要全局开 patch。需要兜底时，直接 `import { CapacitorHttp } from '@capacitor/core'`，只对我们的 AI 请求显式调用它。**

### 6.4 ⛔ 在 Capacitor 里用 History 路由 + `file://`

`server` 配置文档里有一句容易忽略的话（[Config](https://capacitorjs.com/docs/config)）：
> "Custom schemes on Android are unable to change the URL path as of Webview 117. Changing this value from anything other than `http` or `https` can result in your application unable to resolve routing. **If you must change this for some reason, consider using a hash-based url strategy**"

**对策**：用 **hash 路由**（`#/chat`、`#/settings`）或干脆不用路由（纯状态机切屏）。这也让 GitHub Pages 部署零配置（不需要 404 fallback 重写）。

### 6.5 ⛔ 把 Key 放进 URL / 放进构建产物 / 放进日志

- URL query 会进历史记录、Referer、CDN 日志；
- `.env` 里的 `VITE_*` 变量**会被内联进 bundle**，等于公开（Capacitor 官方安全文档明确警告 "never embed secrets in your app code"）；
- 调试时 `console.log(headers)` 会把 Key 写进用户手机日志。
**对策**：Key 只从 IndexedDB 读、只放 `Authorization` 头、日志脱敏（`sk-***`）。

### 6.6 ⛔ 用整页 `innerHTML` 重渲染

聊天流式输出 + 果冻动画 + 输入框焦点，这三样里任意一样都会因为整页重绘而崩坏（输入法被弹回、动画被重置、滚动位置跳顶）。**对策**：DOM 增量更新，只 append 新消息节点；输入框永远不重建。

### 6.7 ⛔ CI 里的其他小坑
- `npx cap sync` 之后 `android/app/build.gradle` 里的**自定义签名代码不会被覆盖**（Capacitor 只改 `capacitor.build.gradle`），可以放心改；但 `npx cap add android` **会覆盖整个 `android/` 目录**，别重复执行。
- **`./gradlew` 记得 `chmod +x`**（从 Windows 提交的仓库会丢执行位，CI 会报 `Permission denied`）。
- **`actions/upload-artifact` 的 `if-no-files-found: error`** 一定要加，否则构建失败时你只会看到一个空 artifact，白排查半小时。
- **别用 `ubuntu-latest`**（见 §3.5 第 2 条）。

### 7.3 请求层设计（最关键的一个文件）

```ts
// src/ai/client.ts —— 全项目唯一发 HTTP 的地方
export type ChatResult =
  | { ok: true; text: string }
  | { ok: false; kind: 'cors' | 'auth' | 'rate' | 'quota' | 'net' | 'server' | 'abort'; message: string; raw?: unknown };

export async function chat(cfg: ApiConfig, msgs: ChatMessage[], signal?: AbortSignal): Promise<ChatResult> {
  try {
    if (cfg.mode === 'native' && isNative()) return await viaCapacitorHttp(cfg, msgs); // 无 CORS、无流式、无取消
    return await viaFetch(cfg, msgs, signal);                                          // 有 CORS 风险、可流式、可取消
  } catch (e) {
    // 浏览器不允许我们读取真实原因，只能按"是否收到过任何响应"来分类
    return classify(e);   // TypeError + 从未收到响应 → 高概率是 CORS 或网络层被阻断
  }
}
```

配套的错误文案（**这一屏决定了用户会不会放弃**）：
| 分类 | 中文提示 | 建议动作 |
|---|---|---|
| `cors` | 该接口不允许网页直接访问（CORS）。 | ① 换一个接口地址 ② 用「兼容模式」（仅 App 内可选）③ 看帮助里的"自建转发" |
| `auth` | API Key 不对或已失效（401）。 | 检查 Key 有没有复制全、有没有多空格 |
| `quota` | 余额不足或额度已用完（402/403/429）。 | 去服务商后台看余额 |
| `net` | 连不上这个地址（可能是网络/地区限制）。 | 试试能不能在浏览器打开服务商官网 |
| `server` | 服务端返回了错误（5xx）。 | 稍后再试 / 看原始报错 |

**还有一个必须做的小事**：在 App 内提供"查看原始错误"折叠区（把 `e.message` 和我们可以拿到的 status 展示出来）——**社区支持成本会因此降一个数量级**，因为用户能自己把原因截图发给我们。

### 已核实但容易搞错的几件事（供交叉检查）

- **Remix Icon 的许可证已经不是 Apache-2.0**：npm 元数据仍写 `Apache-2.0`，但仓库 `LICENSE` 文件已换成自定义的 *Remix Icon License v1.0 (2026-01)*，禁止转售图标包/做竞争性图标库。开源项目用它要留个心眼。
- **Lucide 是 ISC**：GitHub 的 license 自动识别显示为 `Other`，但 `LICENSE` 文件原文第一行就是 `ISC License`。
- **CapacitorHttp 的 `allow-credentials: true` + `Access-Control-Allow-Origin: *` 同时出现的问题**：我在测 SiliconFlow 时看到它同时返回 `ACAO: *` 和 `ACAC: true`——按 CORS 规范，**带凭据的跨域请求不允许用 `*`**，浏览器会拒绝。我们不带 cookie 发请求（`credentials: 'omit'`，默认就是 omit），所以不受影响；但如果将来某个代码路径用了 `credentials: 'include'`，就会直接失败。
