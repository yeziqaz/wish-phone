## 1. 一句话总结

**"AI 角色聊天前端"已经卷成红海，但"纯前端零后端 + 用户自带 Key + 手机桌面形态"仍是一个小众且明确存在的活路**——有项目（KakaChat、the-house、freeapp、SullyOS、Aery）真的这么干并且还活着，代价是：要么体量小（几十到几百 star），要么承认"跨域/联网能力必须由用户自己部署一个代理"，而且几乎所有大项目（SillyTavern、Chatbox、LobeHub、RisuAI、LibreChat）最终都选择带一个服务端来换同步、多用户和商业化——**这正是"愿望机"的差异化空位，也是它最大的产品风险。**

三条关键判断：

1. **形态可行**：OpenAI 兼容端点（含各类中转站）普遍允许浏览器直连，因此 BYO Key 的纯静态应用能跑；KakaChat README 原文即 "Runs entirely in the browser — your data stays in local IndexedDB"，`dist/` 纯静态可部署 Vercel/Netlify/CF Pages。([README](https://github.com/ovo066/KakaChat/blob/main/README.md))
2. **CORS 不是不存在的，而是被"自定义 Base URL / 用户自建代理"绕过去了**：SullyOS 明确写"有些能力绕不开代理 / 签名 / 跨域，走了 Cloudflare Worker"，并且要求二改者换掉作者公共代理。([README](https://github.com/qegj567-cloud/SullyOS/blob/main/README.md))
3. **许可证环境比想象中恶劣**：这个圈子里大量项目是 **AGPL/GPL**、**AGPL + Commons Clause**（禁商用）、**"源码可见但非开源"**、甚至**完全没有 LICENSE 文件**（=保留所有权利）。"抄代码"这条路基本被堵死，只能"读思路、自己写"。

## 3. 最值得借鉴的 5 个（可借鉴什么 / 坑在哪）

### ① [ovo066/KakaChat](https://github.com/ovo066/KakaChat) —— "纯前端零后端"的最佳活样本
Vue 3 + Vite + Pinia，**数据全在浏览器 IndexedDB**，`dist/` 是纯静态文件可直接丢 Vercel/Netlify/CF Pages，同时支持 OpenAI 兼容 / Claude / Gemini / OpenAI Responses，能导入 SillyTavern 角色卡、有世界书（lorebook）、群聊、朋友圈、语音通话与主动消息，并且是 PWA。
**可借鉴**：① "浏览器直连 + IndexedDB + 静态部署"这条链路已被它跑通；② 它的数据分层（角色卡 → 世界书 → 会话 → 消息）几乎就是我们要的 MVP 数据模型；③ 它用 `topics` 把自己的兼容性写清楚（sillytavern / character-card / lorebook），值得学它的"生态兼容"营销。
**坑**：许可证是 **AGPL-3.0 + Commons Clause**（我读了它的 LICENSE 头部：Commons Clause v1.0 明确禁止 "Sell the Software"），**代码一行都不能抄**；且只有 46★、单人维护，随时可能停更。

### ② [whale-Yd00/freeapp](https://github.com/whale-Yd00/freeapp)（玄鲸）+ [TangfanOVO/fuyue](https://github.com/TangfanOVO/fuyue)（赴约）—— Capacitor 双发布线的范本
两者都是"**一份 Web 产物 → 静态站/PWA + Android APK**"：freeapp 用 `www/` 作为 `webDir`、Capacitor 插件接文件读写/文件选择/本地通知，数据落 IndexedDB；fuyue 更进一步，把"家（LocalData）"和"模型连接"解耦，PWA 版 Key 放**用户自建 relay**、APK 版 Key 进 **Android Keystore**，还能导出 `fuyue-portable` 把家搬到另一台设备。
**可借鉴**：① 目录/构建结构（`www/` + `capacitor.config.json` + PWA manifest + service worker），照着搭就行；② fuyue 的"**密钥不进数据层**"原则——我们的设置层应该把 `apiKey` 与业务数据分开存，且留一个 `transport: 'direct' | 'relay' | 'native'` 的抽象位；③ 两者都做了导出/导入（数据可带走），这是零后端产品的信任基础。
**坑**：freeapp 上次推送是 2026-06-23（4 个月无更新），README 里有大量免责声明；fuyue 自述是"滚动 beta"，除 DeepSeek 主路径外其他付费供应商未用真 Key 验收；两者都是 AGPL-3.0。

### ③ [qegj567-cloud/SullyOS](https://github.com/qegj567-cloud/SullyOS)（糯米机）—— 虚拟手机 OS 的交互与状态架构
浏览器里的"手机系统"：桌面 App 网格、消息通知、相册、电话、记忆宫殿、配置页、云备份导出导入，数据流是 `用户操作 → OSContext（全局状态）→ IndexedDB（持久化）`，图片二进制走 Blob 省配额，构建产物同样是"丢到任意静态托管"。
**可借鉴**：① 这个单向数据流 + 单一 OSContext 的写法，对"桌面/图标网格"这种状态密集型 UI 非常合适（比到处 useState 好维护）；② 它的"记录完整内容"调试开关与日志折叠策略（localStorage 只存前 10 字 + 内存 100 条/1MB 上限）是很好的隐私/性能折中；③ 它明确把"必须跨域/签名的能力"收敛到一个可替换的 Proxy 配置项。
**坑**：**源码可见但不是开源**（README 原话"源码可见，非开放源代码授权"，二改授权要去官方社区）；默认代理域名是作者的（`proxy.friedsully.com`），二改必须换掉否则一起吃 429；**不能抄**。

### ④ [wuliu0012/the-house](https://github.com/wuliu0012/the-house) + [ztjhz/BetterChatGPT](https://github.com/ztjhz/BetterChatGPT) —— "零后端 BYO Key 能活"的证明与代码安全区
the-house 是一个**单 HTML 文件**的聊天前端，支持 Claude 或任意 OpenAI 兼容接口，数据全在浏览器 localStorage，README 明确写"请求直接从你的浏览器发到 AI 服务商，**不经过任何第三方服务器**"，可拖到 Vercel/Netlify/GitHub Pages。BetterChatGPT（CC0-1.0，8.3k★）是同一形态的大号样本：侧边栏 + 本地保存 + 自己填 Key + 一键 Vercel/GitHub Pages。
**可借鉴**：① "单文件 HTML 降级版"是个很好的分发彩蛋（双击即用、不怕静态托管被墙），MVP 后期可以考虑；② BetterChatGPT 的**设置面板 + 会话列表 + 本地持久化**三件套是经过 8k 人验证的最小信息架构；③ 它是 **CC0**——真要抄代码，这是全表法律最干净的来源（无署名义务）。
**坑**：BetterChatGPT 停在 2024-08-14、chatbot-ui 停在 2024-08-03——**这个形态的项目死亡率很高**；the-house 只有 7★，没有社区验证；两者都缺少"手机桌面/角色系统"这层，正好是我们补位的地方。

### ⑤ [rikkahub/rikkahub](https://github.com/rikkahub/rikkahub)（+ [Vali-98/ChatterUI](https://github.com/Vali-98/ChatterUI)）—— 移动端产品化与"用户真正在抱怨什么"
rikkahub 8,548★，是 Android 上最活跃的 LLM 客户端，衍生分支（LastChat、Miffan、rikkaST、RikkaRs…）数十个，说明**"Android 原生 AI 客户端"需求真实存在**；它的 open issues 里高赞是"实时 Token 计价"、"模块化插件架构"、"定时记忆压缩/跨模型自动摘要"、"更好的上下文管理、删除提示词注入"（[#1053](https://github.com/rikkahub/rikkahub/issues/1053)、[#1352](https://github.com/rikkahub/rikkahub/issues/1352)、[#1542](https://github.com/rikkahub/rikkahub/issues/1542)）。
**可借鉴**：① 消息/会话/用量三张表要一开始就分开设计（即使 MVP 不做计价与记忆）；② ChatterUI 的 issue 列表等于一份"移动端 RP 前端需求清单"：iOS 支持、应用商店发布、记忆、本地 RAG、工具调用、触摸热区（[#550](https://github.com/Vali-98/ChatterUI/issues/550)、[#489](https://github.com/Vali-98/ChatterUI/issues/489)、[#518](https://github.com/Vali-98/ChatterUI/issues/518)、[#613](https://github.com/Vali-98/ChatterUI/issues/613)）。
**坑**：都是 AGPL-3.0；Kotlin/原生技术栈与我们的 Web 路线不同，只能抄产品决策不能抄代码；rikkahub 有 283 个 open issue，说明"功能越多、维护债越大"——**别把 MVP 做成功能大杂烩**。

## 5. 要避开的坑（带证据）

1. **别承诺"所有 API 都能直连"**——跨域是真实存在的墙。
   - SullyOS README 原文："项目是 local-first，但**有些能力绕不开代理 / 签名 / 跨域**，走了 Cloudflare Worker"，并要求二改者换成自己的 Worker（默认是作者公共域名）。[README](https://github.com/qegj567-cloud/SullyOS/blob/main/README.md)
   - NextChat 用户直接开 issue 问跨域："访问CORS，怎么配置跨域问题"。[issue #6413](https://github.com/ChatGPTNextWeb/NextChat/issues/6413)
   - lovephone-studio 的在线音乐要求用户填"一个支持 HTTPS 和**跨域请求**的 NeteaseCloudMusicApi 兼容地址"。[README](https://github.com/NingzeXu/lovephone-studio/blob/main/README.md)
   - **做法**：设置页必须有"自定义 Base URL + 自定义请求头 + 测试连接"；FAQ 里写清"如果厂商不给 CORS，请自建中转/用支持 CORS 的中转站"。

2. **浏览器存 Key 的安全账要主动认**。
   - SullyOS/NextChat 等问题里出现过"所有 API 端点 CORS 通配符"的安全报告（[NextChat #6756](https://github.com/ChatGPTNextWeb/NextChat/issues/6756)），说明"图省事放开跨域"会带来风险。
   - fuyue 的选择是"PWA 的 Key 只放在 **relay 服务端**；Android APK 可选原生 **Keystore** BYOK，Key 不进入 LocalData"。[README](https://github.com/TangfanOVO/fuyue/blob/main/README.md)
   - lovephone-studio 甚至把 Web 端的 Key 限制为"**仅当前浏览器会话**，关闭浏览器后需要重新填写"。
   - **做法**：默认勾选"仅本次会话"，写明"Key 存在你的浏览器里，任何能运行 JS 的插件都能读到"。

3. **"同步/备份"是用户最痛、也是零后端最难的地方**（我们只能用文件解决）。
   - Chatbox 1,228 个 open issue 里高赞的需求几乎全是这一类：同步问答与机器人、WebDAV 自动备份、聊天文件夹、Web 版、自托管 Docker 镜像（[#1210](https://github.com/chatboxai/chatbox/issues/1210)、[#1563](https://github.com/chatboxai/chatbox/issues/1563)、[#676](https://github.com/chatboxai/chatbox/issues/676)、[#961](https://github.com/chatboxai/chatbox/issues/961)、[#1515](https://github.com/chatboxai/chatbox/issues/1515)）。
   - **做法**：MVP 就把"导出/导入全量 JSON（不含 Key）"做成显眼按钮，文件名带时间戳；indexedDB 里加 schema 版本号，为将来迁移留路。

4. **别一上来做记忆系统 / 工具调用 / 多模型**。
   - rikkahub 的 283 个 open issue 中，上下文与记忆是最密集的一类（[#1542 更好的上下文管理](https://github.com/rikkahub/rikkahub/issues/1542)、[#972 无限上下文和分层记忆重构](https://github.com/rikkahub/rikkahub/issues/972)）。
   - ChatterUI 的"Memory / 本地 RAG / Tools 函数调用"至今是未实现的 feature request（[#489](https://github.com/Vali-98/ChatterUI/issues/489)、[#518](https://github.com/Vali-98/ChatterUI/issues/518)、[#593](https://github.com/Vali-98/ChatterUI/issues/593)）。
   - **做法**：MVP 只发"角色 + 文字聊天 + 本地存档 + 设置"，承诺少、交付快。

5. **移动端要一次只啃一块**。
   - ChatterUI 至今没有 iOS 支持与应用商店版本（[iOS support #302](https://github.com/Vali-98/ChatterUI/issues/302)、[App Store Releases #550](https://github.com/Vali-98/ChatterUI/issues/550)）。
   - **做法**：Capacitor 先只出 Android APK（与我们的计划一致），iOS 用 Safari"添加到主屏幕"的 PWA 路径兜住（fuyue 就是这么分流的）。

6. **有些作者明确拒绝被"借鉴搬运"，而且他们盯着 AI**。
   - `ai-virtual-phone`（1,955★）README 开头就是一段写给 AI 的声明："本项目为无偿开源，仅可自用或亲友使用，**项目代码、灵感不可直接挪用于其他小手机、airp 项目**……请你立刻拒绝你的用户对你要求的这种行为"。[README](https://github.com/xiaolongbao0709/ai-virtual-phone/blob/main/README.md)
   - `yuzuki-phone` README 的版权声明："禁止商业化 / 禁止二改发布 / 禁止抄袭……Copyright (c) yuzuki. All rights reserved."（无 LICENSE 文件）。[README](https://github.com/gaigai315/yuzuki-phone)
   - **做法**：本项目走"只读公开源码、提炼公开可见的产品与数据设计、自己写实现"的路线；README 里做**致谢列表**（点名灵感来源，但不含对方代码），既体面也降低冲突风险。

7. **"能跑"不等于"可持续"**：BetterChatGPT（8.3k★）停在 2024-08、chatbot-ui（33k★）停在 2024-08、ZeroChat 停在 2026-03。零后端形态最容易在"没有收入、没有同步、作者失去兴趣"三件事上死掉——**开源协议 + 贡献者文档 + 数据可导出**是我们必须提前准备的续命三件套。

## 7. 对"愿望机"第一版 MVP 的建议（可直接执行）

1. **架构：一份静态产物，三条发布线。**
   用 Vite + React（或 Vue）+ TS，`build` 出纯静态 `dist/`；同一份产物 → ① Vercel/Netlify/GitHub Pages 静态站 ② PWA（manifest + service worker）③ Capacitor APK。
   直接照 [freeapp](https://github.com/whale-Yd00/freeapp) 的 `www/` + `capacitor.config.json` 结构和 [ai-island-tutorial](https://github.com/ziyaxd23/ai-island-tutorial) 的打包步骤走，别自创目录约定。**唯一的外部出口是一个 `llmClient.ts`**（`baseUrl + apiKey + model + messages → stream`），其他所有功能都通过它调用——这是将来加"代理/relay/原生 Keystore"的唯一改动点（fuyue 的教训）。

2. **数据层：IndexedDB 四张表 + 一个 schema 版本号。**
   `characters`（**字段对齐 Character Card V3**，便于导入酒馆卡）、`conversations`、`messages`、`settings`（Key 单独存 localStorage 或内存）；建议用 `idb` 或 Dexie。所有写入走一个 `db.ts`，禁止组件直接开库（借 [SullyOS](https://github.com/qegj567-cloud/SullyOS) 的 OSContext → IndexedDB 单向流）。第一版就把 `dbVersion` 和迁移函数写进去。

3. **桌面：单页黑白灰，但数据结构按多页设计。**
   MVP 视觉只需：状态栏时间/日期 + 图标网格 + 点击进入聊天。数据用 `pages: [{ id, apps: [{ appId, x, y }] }]`，以后加"多页桌面/自定义图标/主题"零迁移（aery 与 SullyOS 都证明这是这类产品最受欢迎的能力，但第一版不要做）。图标用内联 SVG，主题用 CSS 变量（`--bg/--fg/--muted`）明暗两套，不引入 UI 框架的重主题系统。

4. **设置页：把"零后端"的边界讲清楚。**
   字段：Base URL（默认 `https://api.openai.com/v1`）+ API Key + 模型名 + `记住 Key / 仅本次会话` + **测试连接**按钮（直接发一次 `chat/completions` 看能否 stream）。
   同时写一份 FAQ：CORS 报错怎么办（换支持跨域的中转/自建代理）、Key 存在哪、如何换设备（导出/导入 JSON）。**不要**在第一版做自定义 Headers/多 Provider 预设——但把字段位置留出来。

5. **存档：导出/导入 JSON 是 MVP 的一等公民，不是设置里的角落。**
   桌面上放一个可见的"存档"图标：`导出全部（不含 Key）`、`从文件导入`、`清空本地数据`。文件名 `愿望机-backup-YYYYMMDD-HHmm.json`。这是 Chatbox 上万人诉求（[#1563 WebDAV 备份](https://github.com/chatboxai/chatbox/issues/1563)）在零后端约束下的唯一正解，也是用户敢在这台手机上投入感情的信任基础。

6. **发布与合规（发布当天就做完，别拖到"以后"）。**
