## 0. 为什么写这一份

用户在验收加号扩展抽屉时提了两条批评，两条都成立：

1. **抽屉排版没做完**：一排图标横着铺在最上面，方框下面空出一大条。看起来像"把一排按钮塞进一个盒子"，而不是"设计了一个面板"。
2. **括号动作破坏线上聊天的代入感**：`(尾巴一甩，从屏幕边角探出半个脑袋) 呜……你终于来啦。` 这种写法是角色卡的常见格式，但直接躺在气泡里，就把"和朋友在手机上聊天"演成了"读剧本"。

这份调研的用途是：**把这两件事的度量依据和取舍写死**，以后改这块不用重新拍脑袋；下一批界面（角色卡、世界书）也照这个流程先调研再动手。

| 微信 / QQ 加号面板的**官方**设计稿数值 | — | ❌ **未核实**（腾讯没有公开设计规范，本次也未做开放网络检索） |

> 结论：**微信/QQ 的具体像素值没有官方公开来源可引。** 所以下面给的是"照它们的结构与节奏对齐"+ 用本仓库自己的令牌算出的度量，并附推算验证，而不是假装引用了权威规范。

### 1.2 从参考截图里读出来的结构（非数值）

用户提供的两张微信截图（`28809.jpg`、`28811.jpg`）能读出的**结构性**事实：

- 面板是一个**贴着键盘高度的整块方框**，背景比消息区浅一档；
- 内部是**每行 4 个的方格**，一行放满再换行；
- 每个方格 = 圆角方底 + 描边图标 + 下方 12px 左右的小字标签；
- 条目不止一屏时，底部有一排小圆点表示「还有下一页」。

对照 2026-11-08 的实机截图（`28808.jpg`），我们的实现当时是：**一排横向 flex + 横向滚动**，所以
① 第 6 个条目被挤出屏幕（截图里能看到半截 `[vertex]cl…`）；
② 横条只占方框顶部一条，下面全空。

### 1.3 落地规则（写进 `chat.css` 的约束）

| 项 | 取值 | 依据 |
|---|---|---|
| 每行条目数 | **4** | 与微信/QQ 的节奏一致 |
| 条目宽度 | `calc((100% - 3 × --sp-2) / 4)`，上限 88px | 390px 屏 = 83.5px/列 |
| 图标底 | 56×56，`--radius-lg`（14px），`--surface` + `--line` 描边 | 项目令牌 |
| 标签 | `--fs-caption`（12px），`--ink-2`，单行省略号 | 12px 是项目字号下限 |
| 行/列间距 | 行 `--sp-3`(12) / 列 `--sp-2`(8) | 8 的倍数 |
| 不足一行时 | **居中**，不左对齐留半排空位 | 见下 §1.4 |
| 面板高度 | `max(180px, 最近一次键盘高度 - 键盘仍占用的可视区)` | 键盘↔面板切换时底栏不跳高 |
| 条目在方框内 | **垂直居中**（`align-items:center`），不是顶头排 | 直接回应"下面空一长串" |

**为什么用 flex 换行而不是 `grid`**：`grid` 的 4 列布局在"只剩 2 个条目"时会把它们钉在第 1、2 列，右边空两格，看起来是没做完；
`flex-wrap` + `justify-content:center` 能让最后一行自动居中，成为**有意为之**的样子。这一条被写进了 CSS 注释，防止以后有人"顺手改回 grid"。

### 1.4 390px 屏宽下的推算验证（无截图时的核对方式）

```
可用宽 = 390 − 2×16（页面留白 --sp-4）           = 358 px
每列宽 = (358 − 3×8) / 4                        = 83.5 px
  图标 56 两侧各余 (83.5−56)/2 = 13.8 px   → 放得下
  标签上限 68 px                            → 放得下
每项高 = 上下 8 + 图标 56 + 间隙 4 + 标签 17      ≈ 85 px
2 行 + 行距 12                                  = 182 px
方框内容区高 ≈ 280（键盘）− 上下 padding 20       = 260 px
居中后上下各留白 = (260−182)/2                   ≈ 39 px
```

结论：不再有"顶部一排、下面全空"的问题；上下留白对称，是有意的呼吸感。

## 2. 「沉浸式线上聊天」与括号动作

### 2.1 问题定义

角色卡（Character Card V2/V3）生态里，动作与神态的默认写法就是**圆括号包住**，并且大量卡片的 `first_mes` 就是这么写的。
所以我们**不能**靠"让模型别写括号"来解决——那会跟用户导入的现成角色卡打架。

正确的拆法是**表现层处理**：模型照旧输出，界面把动作**剥出来换个地方放**。

### 2.2 本次采用的方案（用户已确认）

> 用户确认的选项：「独立气泡或沉浸式小窗展示」

- **解析**：`src/apps/chat/room/action.ts` 的纯函数 `parseCharacterAction()`，
  识别**整条消息最前面**的一对 `(……)` 或 `*……*`，返回 `{ actionText, mainText }`。
- **呈现**：`actionText` 渲染成气泡**上方**的「此刻」小胶囊（图标 = 新增的 `sparkle` 四角星，`--fs-caption`，`--surface-2` 底 + `--line` 描边）；
  收起时单行省略号，**点一下展开全文**，再点收回。
- **气泡本体**：只放 `mainText`，也就是"说出口的话"。
- **只处理角色的消息**：用户自己写的括号是他自己的口吻，绝不动。
- **引导模型**：`buildSystem()` 里加了一条 `【动作描写】`，要求动作写在整条消息**最前面**的一对圆括号里、不要写在句子中间、不要用星号。
  这一步是让解析**稳定命中**，不是禁止动作。

配套：`tests/chat-action.test.ts` 覆盖"能拆出括号动作"和"没有动作时原样返回"两种情形，防止以后改正则改坏。

### 2.3 还没做、需要排期的部分

用户原话里还有一个更完整的设想，本次**没做**，先记着：

| 想法 | 状态 | 说明 |
|---|---|---|
| 「心声」（角色心里话）单独一个入口/小窗 | ❌ 未做 | 需要在提示词里约定一种**可解析**的心声标记，否则和普通文本分不开 |
| 「线下聊天模式」开关 | ❌ 未做 | 开启时动作就留在气泡里（适合剧本式扮演）；关闭时走「此刻」小窗 |
| 动作小窗复用到开场白（`first_mes`） | ✅ 已自动生效 | 开场白也是一条 assistant 消息，走同一条渲染路径 |

## 5. 气泡框 / 头像框美化（2026-11-10）

### 5.1 参考来源与许可

用户提供的 `yeziqaz/test`（糯叽叽 / wuli 小手机）**是用户自己的仓库**，License 不成问题，但它是 **Vue + css-tree** 的技术栈，
本项目是**原生 DOM + 设计令牌**，所以只取「数据结构长什么样」，代码全部重写。

本次实际读到的文件（已 clone 到 `/tmp/wuli-test`，仅作分析，不进本仓库）：

| 文件 | 读到了什么 |
|---|---|
| `frontend/src/store/chat-beauty-data.js` | 数据结构：`participants.{user,wuli}.{avatar,bubble}`，气泡字段 = `fill / border / borderWidth / radius / shadow / opacity / gradientColor / gradientAngle`；挂件字段 = `frameId + stickers[]` |
| `frontend/src/apps/chat/chat-beauty-css.js` | 把上面这些字段映射成 `--chat-beauty-*` CSS 变量的那层胶水 |
| `frontend/src/components/CharacterAvatar.vue` | 头像挂件用 **CSS mask 挖空中心**（`radial-gradient(circle closest-side, transparent 33.3333%, #000 calc(33.3333% + .5px))`），保证任何贴纸都不会挡脸 |
| `frontend/src/components/AvatarPendantFrame.vue` | 头像框是**纯 SVG，viewBox 100×100**，`currentColor` 描边，靠 `stroke` / `text` 画花瓣、猫耳 |

### 5.2 不能照搬的三点

| 它的做法 | 为什么不能照搬 |
|---|---|
| 气泡默认色 `#A6E976`（草绿）、`#F7D7E3`（粉） | 本项目宪法 §3.1 禁裸色值；视觉基调是**黑白灰 + 描边线框** |
| 全套「软萌可爱 / 马卡龙 / 梦幻」预设 | 与本项目视觉不符。用户已明确「画风跟我们不匹配，改成本项目的画风」 |
| 任意 `customCss` 注入 | 违规风险高（能选到 `html`/`body`），本项目不开放自由 CSS |

**保留的是它的骨架**：`participants.{自己,对方}.{avatar,bubble}` 这两层结构，以及 `frameId` 用**内置 id 而非图片 URL** 的思路
（零网络请求，符合「纯前端零后端」）。

### 5.3 本项目采用的取值

因为视觉基调是黑白灰，气泡**不能用颜色区分说话人**，只能用**底面明暗 + 描边**区分，这本来就是现在的做法：

| 项 | 自己 | 对方 | 依据 |
|---|---|---|---|
| 底面 | `--inverse-bg`（近黑） | `--surface`（白） | 沿用现状 |
| 文字 | `--inverse-ink` | `--ink` | 沿用现状 |
| 圆角 | `16px`，右上角 `4px` | `16px`，左上角 `4px` | 微信/QQ 的「尖角指向说话人」 |
| 描边 | 无 | `--border-w solid --line` | 反色块本身已有边界，再描边是双框 |

**美化只做「可调」的部分**：圆角大小、阴影强弱、气泡最大宽度。**不做**换色，因为换色会立刻破坏黑白灰基调。

头像框：`viewBox 100×100`、`currentColor` 单色描边、`stroke-width 2`，与项目里已有图标同一套线条语言。
头像框**永远不填色**，只描边——这样叠在黑白灰头像上不会脏。

### 5.4 未核实

- 微信 / QQ 的气泡圆角与描边的真实像素值：**未核实**（腾讯未公开）。本项目用的是自有 `--radius-*` 令牌与 16/4 尖角。

## 6. 一轮多气泡 + 字数规则（2026-11-10）

### 6.1 问题

豆包 / 微信的对话是「一条消息 = 一句话」。现在本项目一轮 = 一个大气泡，长回复读起来像文章。

### 6.2 规则（写成可调常量，用户后面自己改）

| 规则 | 取值 | 理由 |
|---|---|---|
| 一轮气泡数 | 2~8 | 少于此没有「连发」感；多于此刷屏 |
| 单气泡字数 | 1~60 | 微信一条消息通常 1~2 行；60 字≈3 行，超过就该换口气 |
| 拆分依据 | 换行 | 模型本来就用换行分段，不用另造标记 |

### 6.3 正则 / 预设的位置

用户要的是「聊天 APP 里定一个正则」，所以：

- 解析函数放 `src/apps/chat/room/split.ts`（**纯函数，可单测**）
- 规则常量集中在文件顶部，用户改数字即可，不用碰逻辑
- 动作剥离（`chat-action.ts`）与气泡拆分（`chat-split.ts`）**串联**：先剥动作，再拆气泡

## 8. 按角色定位区分聊天风格（2026-11-10 第三批）

### 8.1 为什么要分开

用户原话：「wuli 的定位是用来处理问题的，而其他角色则是用来角色扮演的。」

这两类需求是冲突的：

| 角色类型 | 典型任务 | 合适的消息形态 |
|---|---|---|
| wuli（内置） | 写代码、改界面、做角色卡、查资料 | **一个长气泡说完**，代码整块贴 |
| 其他角色 | 角色扮演、谈恋爱、剧情推进 | **2~8 个短气泡**，像真人连发 |

如果把「2~8 气泡 / 单条 ≤60 字」硬套到 wuli 身上，让它讲一段改界面的步骤，会被切成
「第一步」「第二步」…… 读起来支离破碎，反而更费劲。

### 8.2 为什么写在代码里，不做成「内置世界书」

考虑过三个位置，最后选代码常量：

| 方案 | 问题 |
|---|---|
| 内置世界书 | 世界书是**用户数据**（IndexedDB）。要做到「用户看不见、改不了」，得给 `Worldbook` 加 `builtin` 标记、在角色档案页和设置页两处列表过滤、还要挡住删除。为了装一段固定文字，多出三处特判 |
| 正则 | 正则只能**事后改文本**，没法告诉模型「该怎么写」；也识别不了代码块结构 |
| **代码常量**（采用） | 用户同样看不见、改不了、不占数据库；`chatStyleRules()` 一处定义，`chat-split.ts` 顶部常量一处调数字 |

判定依据用现成的 `character.builtin`（`src/core/types.ts:183`），不需要新字段。

### 8.3 代码块保护（关键修复）

上一版 `splitIntoBubbles()` 有真 bug：代码块里的换行会被当成气泡断点，
一段 10 行的代码会被拆成 10 个气泡。本批修掉：

`PASSTHROUGH_PATTERNS` 里这些整块保留、绝不拆：

| 形态 | 正则判据 |
|---|---|
| ``` 围栏代码块 | `/^```[\s\S]*?```$/` |
| Markdown 表格 | 表头行 + `\| --- \|` 分隔行 |
| 命令行 | 行首 `$` 或 `>` |
| 缩进代码 | 行首四空格或制表符 |

另外「超上限合并短行」时也**跳过固定块** —— 代码块不会被并进别的气泡。

单测从 7 条加到 11 条（总数 59 → 63），新增 4 条覆盖：代码块整块保留、代码内换行不拆、
表格整行保留、合并时不把代码块并走。

### 8.4 内置角色卡只读

`src/apps/character/character-edit.ts`：`character.builtin === true` 时

- 所有 `input` / `textarea` 设为 `readOnly`（**不是隐藏** —— 用户看得见人设，才知道 wuli 为什么这么回话）

## 9. 括号回退事故与修复（2026-11-10 第四批）

### 9.1 出了什么问题

用户反馈：「怎么又变成了括号气泡里面有括号？都说了动作描写和心理描写是独立出来的。」

**这是我的实现错误，不是理解错误。** 上一批我把开关的语义写反了：

| | 错误实现 | 应该是 |
|---|---|---|
| 开关**开** | 剥离动作 + 显示星标 | 剥离动作 + 显示星标 |
| 开关**关** | **不剥离**，原文照显示 ❌ | **仍然剥离**，只是不显示星标 |

后果：用户关掉开关（默认态）后，`（尾巴一甩）我在呢` 这种原文直接进了气泡，
括号又回来了 —— 正是用户一开始要求消除的东西。

### 9.2 正确的语义边界

**「剥离」是表现层的固定规则，不是可选项。**

- 气泡 = 角色说出口的话（线上聊天里人只会打字，不会把动作写成括号）
- 动作/心理 = 旁白，属于附加信息
- 开关只决定**旁白要不要给出一个入口**（那枚星标）

所以：

```ts
// 不管开关开没开，角色消息一律剥离
const parsed = !isUser && !imageUrl
  ? parseCharacterAction(message.content)
  : { actionText: null, mainText: message.content };

// 开关只管「要不要渲染星标」
const note = NOTE_TOGGLE_ENABLED && segmentNotes.length > 0 ? noteHTML(segmentNotes) : '';
```

开关关闭时看到的就是**纯对话**，动作内容不会消失（它还在数据库原文里），
只是界面上没有入口 —— 打开开关就能看到。

**没有新建表**。用户身份只有一份、永远只有一份，为此建表要走 schema 迁移，不划算。

### 12.4 顺带修的两个真问题

**① 用户消息没有头像。** 原来 `msg-row--user` 那一侧是空的，
只有角色有头像 —— 不像真在聊天。现在双方都有。
布局本来就有 `flex-direction: row-reverse`，所以自己的头像落在右侧，符合微信/QQ。

**② `{{user}}` / `{{char}}` 从来没被替换过。** `core/types.ts:243` 的注释写着
「用户在这个会话里叫什么（{{user}} 的替换值）」，但代码里没有任何替换逻辑。
后果：角色卡的示例对话里写的是「{{user}}: 你好」，模型收到的是**字面花括号**，
演示中对方永远叫「{{user}}」。

修法：新增 `core/placeholders.ts`，`buildSystem()` 最后统一套一次。

> **实现细节值得记一笔**：最初用 `split('{{user}}').join(name).split('{{char}}').join(char)`
> 串起来写。单测发现，当用户名本身含 `{{char}}` 时，第二步会把刚填进去的文字**再换一次**。
> 改成单次扫描（`startsWith` 逐位前进），一次只认一个占位符，不会二次替换。

### 12.5 一处目录调整（跨屏复用）

引用方从 1 个变成 2 个，属于正当的下沉，不是顺手重构。

| 决定 | 理由 |

| 签名可以空 | 签名是装饰，空着就是「未填」 |

## 13. 气泡框美化（2026-11-10 第八批）

### 13.1 为什么是「档位」而不是滑杆

用户要的是「顺眼」，不是「精确到 13px」。手机上滑杆有两个问题：
手指挡住看不清、松手前的抖动会落在奇怪的值上。

给 3 个已经调好的档，点一下立刻看到差别，比滑杆快也比滑杆准。

### 13.2 四组档位与度量

**圆角**（`RADIUS_OPTIONS`）

| 档 | 值 | 位置 |
|---|---|---|
| 小圆 | 10px | 接近 Material 的默认，偏「整齐」 |
| 中圆 | 14px | **默认**。介于微信方角与 QQ 大圆之间 |
| 大圆 | 18px | QQ 手感，再大就成药丸按钮了 |

**宽度**（`WIDTH_OPTIONS`，占消息区百分比）

390 宽屏推算：页面左右各 16 → 可用 358；头像 36 + 间隙 8 → 气泡最多 314。

| 档 | 值 | 实际宽 | 15px 正文约几字/行 |
|---|---|---|---|
| 窄 | 65% | 204px | 13 |
| 中 | 75% | 236px | 15 |
| 宽 | 85% | 267px | 17 |

**上限定在 85%**：100% 时长句会贴到屏幕边缘，失去呼吸感。

**边框**

| 档 | 值 |
|---|---|
| 细线 | `--border-w`（1px） |
| 粗线 | `--border-w-strong`（1.5px） |
| 无框 | `0` |

只影响**角色气泡**。我自己的气泡是反色块（`--inverse-bg`），
黑底再加深色描边看不出来，只会让边缘变毛，所以那边恒为透明边框。

**间距**：紧凑 2 / 正常 4 / 宽松 8。最小值不为 0 —— 否则多个气泡会粘成一坨。

### 13.3 尖角半径的算法

指向说话人的那个角必须比主圆角**小一档**，否则：

- 一样大 → 气泡变成完整圆，看不出方向
- 比主圆角大 → 怪形状

```ts
tailRadiusPx(main) = Math.max(4, main - 10)
```

10 / 14 / 18 → 4 / 4 / 8。单测钉住「永远小于主圆角」和「不小于 4px」。

### 13.4 为什么走 CSS 变量而不是给气泡加 class

一条会话可能有几百条消息。改样式时若重画 DOM，几百个节点的重建会明显卡顿。

挂在 `.chat-page` 上设一次变量，所有气泡自动继承 —— 一次 `setProperty` 完事：

```
--bubble-radius / --bubble-radius-tail / --bubble-max-width
--bubble-border-width / --bubble-gap
```

CSS 里全部带 fallback（`var(--bubble-radius, 14px)`），所以样式没加载时也不会塌。

### 13.5 自检清单结果

| 项 | 结果 |
|---|---|
| 390 宽横向溢出 | 无。分段控件：358 − 36(标签) − 12(gap) = 310，三档各 103px，两字标签 30px 够 |
| 一屏一个主按钮 | ✅ 面板底部只有「好了」 |
| 壳不超过两行 | ✅ 面板无叠层 |
| 字号档位 | 面板内 3 档（capture/sm/lg），合规 |
| 触控 ≥44 | 分段按钮视觉 36，用 `::after { inset: -4px 0 }` 补到 44 |
| 圆角套圆角 | **发现并修掉**：预览块原为 `radius-md`(10)，内层气泡最小 10，改成 `radius-sm`(6) |
| 两个同样重的强调块 | 无。仅面板标题与分组标题，尺寸/颜色不同层 |
| 空状态给下一步 | 不适用（面板无空态） |

### 13.6 常驻可调性

`bubble-tokens.ts` 是纯函数模块，档位数值全部是文件顶部的常量数组。
以后要加档，改数组即可，不用碰逻辑，单测会告诉你有没有越界。

## 14. 朋友圈（2026-11-11 第九批）

### 14.1 数据结构：新增一张表（v5 → v6）

`moments` 表，`keyPath: 'id'`，索引 `byCreatedAt`。

**纯新增，不碰任何已有表** —— 老用户升级后朋友圈是空的，其他数据一个字不动。
`idb` 的 `upgrade` 里只写 `createObjectStore`，没有任何 `deleteObjectStore`。

```ts
interface Moment {
  id: string;
  authorId: string;   // 'me' = 用户自己；否则是角色 id
  text: string;       // 可空（只发图）
  images: string[];   // data URL，最多 4 张
  createdAt: number;
  likes: string[];    // 'me' 或角色 id
  comments: MomentComment[];
}
```

`authorId` 用 `'me'` 而不是给用户造一条角色记录：
不用额外的类型判断，也不会让用户出现在「联系人」列表里。

### 14.2 为什么一条最多 4 张图

图片以 data URL 直接存在记录里（和角色头像同一思路，不为图片单独建表）。

9 张大图会让单条记录到几 MB，每次渲染都要整条读出来，低端机会明显卡。
4 张（2×2 网格）是这个取舍下的上限。要更多图就得给图片单独建表和缩略图缓存，
那是另一个量级的改动。

### 14.3 为什么不做顶部封面

微信放封面是为了展示个人形象，而本项目的「我」板块已经在做这件事。

一块没有真照片的假封面（渐变/纹理都不许用）只是多占 160px，
把动态挤到折叠线以下。直接进 feed 更符合「每个元素都要挣到自己的高度」。

### 14.4 图片网格的三种排法

| 张数 | 排法 | 单格宽 |
|---|---|---|
| 1 | 180px 单列 | 180 |
| 2 / 4 | 两列，最大 200px | 98 |
| 3 | 三列 | 87 |

依据：390 宽屏，列表左右各 16 → 358；卡片内边距 16×2 → 326；
头像 44 + 间隙 12 → 正文列 270。三列时 (270 − 2×4) / 3 = 87px。

### 14.5 就地评论，不弹面板

点「评论」在卡片里展开一行输入框，不弹第二个面板。

理由：评论是一句话的操作，弹面板要多两次点击 + 一次遮罩动画；
就地展开还能让用户看着自己评论的是哪条动态。

回车直接发送（`keydown` 而不是 `<form>` —— 这里不需要表单语义）。

### 14.6 删除用两步确认，不用弹窗

第一次点「删除」→ 按钮变「确认删除」并变红，3 秒内再点才真删。
第二次点之前切走或超时，自动复位。

比弹确认框轻，又比「点了就删」安全。

### 14.7 顺手修掉一个监听器泄漏

上一批的「我」板块每次重画都往 `body` 上 `addEventListener('click')`，
而 `body` 这个元素本身不换（只换 innerHTML）—— 点一下会触发好几遍，
越用越卡，而且会重复写库。

改为每次 `paint` 换一个 `AbortController`，上一次挂的监听器自动失效：

```ts
tabController?.abort();
tabController = new AbortController();
```

`mountMeView` 和 `mountMomentsView` 都接收 `signal`，
所有 `addEventListener` 都带 `{ signal }`。

### 14.8 时间说法

`momentTime()` 抽成纯函数（`moment-time.ts`），因为 `moments-view.ts` 要
import `core/db`，在 node 里跑不起来。

| 距现在 | 说法 |
|---|---|
| < 1 分钟 | 刚刚 |
| < 1 小时 | N 分钟前 |
| < 24 小时 | N 小时前 |
| 昨天 | 昨天 |
| 今年内更早 | M 月 D 日 |
| 跨年 | YYYY 年 M 月 D 日 |

两个边界：**未来时间**（时钟回拨）不许出现「-3 分钟前」，一律「刚刚」；
**跨年前一天但只差 20 小时**，按小时说，不说「昨天」——
「昨天」是给超过 24 小时的跨日准备的。这两条都有单测钉住。
