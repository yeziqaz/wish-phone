# 小世界与记忆设计（草稿）

> 2026-10-31 · 第二版
> 这份文件回答一个问题：**为什么同一个小世界里的哥哥知道男朋友去打球，而闺蜜不知道。**
>
> ⚠️ **只适用于「角色可关联」模式。**
> 「角色独立」模式下，每张卡各跑一条线，不跨角色同步；
> 别人只能以 NPC 身份出现在卡自己的「人物关系」里（见
> [`概念梳理-世界书-身份-好友.md`](概念梳理-世界书-身份-好友.md)）。

---

## 一、四个概念，先分清楚

| 概念 | 是什么 | 例子 |
|---|---|---|
| **小世界** | 一套设定 + 一组角色 + 一个模式 | 「小世界1」 |
| **时间线**（平行时空） | 同一个小世界的一种走向，角色各存一份 | 「这一条里男朋友是陈默」/「这一条里是李明」 |
| **角色** | 小世界里的一个人。没有「主/次」之分，只有「和我什么关系」 | 男朋友、哥哥、闺蜜、同事 |
| **事件** | 发生过的一件事。**记忆的最小单位** | 周六下午，哥哥和男朋友去打球了 |

「主 char / 普通 char」不是两种东西。区别只在**和 user 的关系**，所以角色上有一个字段
`relationToUser`（男朋友 / 哥哥 / 闺蜜 / 同事）。关系是记忆能不能流动的关键。

**小世界之间完全隔离。** 小世界1 里的哥哥，不认识小世界2 里的任何人。
**时间线之间也完全隔离。** 平行时空不是「同一个人的两种记忆」，是两份独立的状态。
**独立模式里，角色之间也隔离。** 角色2 只是角色1 卡里提到的 NPC，不是角色2 自己的那条线。

## 二、记忆怎么流动：三条规则

### 规则 1：一起在场 → 都知道

一件事发生时，在场的人自动知道。

> user 和哥哥、男朋友一起去打球
> → 三个人都有这条记忆

### 规则 2：关系够近 → 会听说

两个人认识，且关系够近，重要的事会「传过去」。亲密度分级：

| 亲密度 | 关系 | 会不会知道对方的事 |
|---|---|---|
| 5 | 恋人、家人、死党 | 基本都知道（除非刻意瞒着） |
| 4 | 好朋友 | 大事会知道 |
| 3 | 普通朋友、同事 | 有交集才知道 |
| 2 | 点头之交 | 几乎不知道 |
| 1 | 陌生人 / 没见过 | **完全不知道** |

> 哥哥和男朋友是好兄弟（5）
> → 哥哥知道男朋友周六去打球；user 问男朋友，他说「跟你哥在一起」
>
> 闺蜜和男朋友不熟（2）
> → 闺蜜**不知道**他去打球
> → 除非：男朋友发了朋友圈，而闺蜜刷到了；或者 user/哥哥跟她提过

### 规则 3：朋友圈 = 广播

发一条朋友圈，等于把事件广播给「能看到的人」。

- 谁能看到：由好友关系 + 可见范围决定（公开 / 仅好友 / 指定人）
- 看到了 → 获得这条事件的记忆，但**只知道朋友圈里写的那些**，不知道细节
- 没看到 → 不知道。**系统不替她脑补**
- 看到是「可能看到」，不是「一定看到」：按活跃度/关系给一个概率，
  这样才不会出现「全世界都第一时间知道」的假感

> 男朋友发了「今天球场手感不错」
> → 哥哥（好兄弟）大概率看到
> → 闺蜜（不熟）小概率看到
> → 同事（陌生人）看不到
> → 但 user 可以截图发给闺蜜，或者直接跟她说 —— 这就成了「user 转述」

### 补充：user 是信息的主要搬运工

user 跟 A 说了 B 的事，A 就获得一条「听 user 说的」记忆。
user 介绍两个人认识，就在关系图里加一条边（从「陌生人」变成「认识」）。

## 三、提示词怎么组装（关键）

每次和角色 X 聊天，只把 **X 视角能看到的东西** 喂给模型：

```
[世界设定]      现代都市，2026 年，你们住在这座城市
[时间线备注]    这一条里，男朋友是陈默
[X 的角色卡]    人设、说话方式、开场白
[X 的关系]      哥哥（亲哥，关系很好）；陈默（男朋友，好兄弟）；你（恋人）
[X 知道的近事]  周六下午：和陈默去打球了（他告诉你的）
                周五晚：user 加班到十点（user 说的）
[不要出现]      user 和闺蜜的私聊、陈默瞒着 X 的事、别的时空的任何东西
```

**不在这份清单里的事，X 就是不知道。** 模型不许自己编。
这是整套设计里最硬的一条：**知识边界由数据决定，不由模型猜。**

## 四、平行时空

- 只有「角色可关联」模式需要时间线；独立模式每个角色天然一条线
- 时间线是**整份复制**的：角色、关系、记忆、朋友圈都复制一份，id 全是新的
- 复制之后两边互不影响：在 A 线删掉一个人，B 线那个人还在
- 切换时间线 = 换一份世界状态，大设定（世界名、世界描述）共用
- 「多个男朋友」的正确用法：
  - 建一条线，男朋友是陈默
  - 复制一条线，把男朋友换成李明
  - 两条线各自发展，互不知道对方存在

> 注意：复制很重（角色多了会慢、会占空间）。第一版只在用户主动点「复制一条新时间线」时做，
> 并且只复制角色卡；记忆和朋友圈的复制等记忆系统做完再补。

## 五、wuli 和「权限」

wuli 是内置的默认小狐狸管家（形象由用户提供）。它不是普通角色卡：

- 第一次打开就有，不需要导入
- 头像、名字、人设是内置的（用户可改，改完就是用户的版本）
- 它以后要能**替你操作这台小手机**：换壁纸、整理桌面、做角色卡、建世界……

所以需要一个权限模型。先定框架，细则等用户想好再填：

| 权限组 | 包含的事 | 默认 |
|---|---|---|
| 外观 | 换壁纸、主题、桌面图标顺序 | 允许 |
| 角色卡 | 新建 / 修改 / 导入角色卡 | 问一下 |
| 世界 | 新建世界、复制时间线、删世界 | 问一下 |
| 聊天 | 读聊天记录、替 user 发消息 | 禁止（必须逐次确认） |
| 系统 | 改 API 服务商、导入导出数据、清空数据 | 禁止 |

三档：**允许 / 问一下 / 禁止**。
「问一下」= 弹一个确认卡片，写清楚要做什么，用户点「好」才执行。
「禁止」= 直接拒绝，并告诉用户去哪开。

> ⚠️ 这一版**只落地了 wuli 这个角色本身**，权限还没有实现。
> 权限真正的价值在聊天和工具调用做完之后，现在做等于空转。

## 六、数据表（下一版要加的）

现在的库（v3）已经有 `worlds` / `branches`，角色上也已经有 `worldId` / `branchId` / `relationToUser`。

记忆系统要加三张表：

```
relationships   关系边
  id, worldId, branchId, fromId, toId,
  type(恋人/家人/朋友/同事/陌生), closeness(1-5), description

events          事件（记忆的最小单位）
  id, worldId, branchId, at, title, detail,
  participants[], location, kind(聊天/朋友圈/手动/系统)

knowledge       谁知道哪件事、怎么知道的
  id, eventId, characterId, branchId,
  level(在场/被告知/刷到朋友圈/听说), learnedAt, fromId
```

朋友圈不单独建表，就是 `events` 里 `kind = '朋友圈'` 的一条，
再加上「谁刷到了」（`knowledge` 里 `level = 刷到朋友圈`）。

**为什么这么拆：**
- 事件只存一份，不重复存 N 份到每个角色身上
- 「谁知道」是独立的一张表 —— 这样删角色、改关系都不用动记忆正文
- 平行时空复制时，三张表按 branchId 整批复制
